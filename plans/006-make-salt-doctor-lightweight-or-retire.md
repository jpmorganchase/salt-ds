## Decision this plan makes

Decide whether the unreleased interactive `salt-ds doctor` shape can meet the
already-frozen packed runtime limits after exactly one bounded correction to
duplicated eager loading.

There are only two successful terminal interpretations:

- `READY_REAL_TASK_EVALUATION`: Doctor is technically fit enough to justify a
  separately reviewed evaluation plan using real, authorized consumer
  repositories and tasks; or
- `RETIRE_INTERACTIVE_DOCTOR`: stop investing in and positioning the
  interactive Doctor command. Preserve the exact-current Knowledge content,
  the five source-bound rules, and analyzer primitives as foundations for
  lighter integrations.

Neither result authorizes production, publication, deployment, participant
contact, installation in a consumer repository, model/network calls, Plan
`005/03`, Plan 003, or a competitor-analysis program.

## Frozen invariants

Every reached unit must preserve all of these:

1. Runtime Doctor invocations are offline. CI may install dependencies and
   transfer exact build artifacts before the invocation, but the Doctor
   process and its worker cannot use the network.
2. Doctor is read-only and never installs, executes, compiles, or edits consumer
   repository code.
3. Package versions, Knowledge bundle version, semantic digest, ruleset,
   findings, coverage, reason codes, exit codes, CJS/ESM behavior, and the
   `salt-doctor-result/1` schema remain exact. The bounded Unit `006/01`
   runtime-source edits are compiler inputs, so compiler and bundle digests may
   change; rebuild and bind them for each candidate, and require parent/worker
   equality within that candidate rather than predecessor equality.
4. The installed binary, not only a programmatic module export, is the runtime
   decision surface.
5. Full Knowledge generation and pack validation remain blocking. Within a
   Doctor process, every artifact actually consumed by the parent or worker is
   digest-verified before it can influence output.
6. The scanner remains isolated in a worker. A missing, crashed, timed-out,
   out-of-memory, malformed, or provenance-mismatched worker fails closed.
7. Existing package-size, result-size, discovery, source, AST, evidence,
   finding, worker-time, worker-heap, and restart ceilings cannot be raised.
8. Terminal Plan 005 plan/control bytes and Plan 004 evidence remain unchanged.
9. AI packages remain private. No AI-package registry lookup, version
   materialization, publication, dist-tag, site, release, deployment, or Plan
   003 change is in scope. Ordinary package-manager dependency resolution and
   integrity-pinned fetches are allowed only during the explicitly identified
   CI `npm ci`/lock-preparation setup and Unit `006/01`'s non-decision packed
   install setup, never during a Doctor invocation.

## Hard complexity budget

These are STOP limits, not targets:

- exactly one Plan 006 runtime measurement/decision executable and its focused
  spec;
- at most two capability-specific Knowledge runtime entrypoints;
- one coherent loading correction: a parser-free static CLI graph, one
  lightweight Knowledge core runtime, and one worker-only review runtime;
- at most one evidence-selected change from the default and project-configured
  maximum of two workers to one reused worker; it is allowed only under the
  condition defined in Unit `006/01`;
- no new runtime dependency, package, output schema, persistent cache, daemon,
  service, shared-memory protocol, native addon, parser fork, generated Doctor
  index, or general benchmark/evaluation framework; and
- no second optimization cycle. A trustworthy final miss is
  `RETIRE_INTERACTIVE_DOCTOR`.

The following tempting changes are explicitly forbidden: lowering the worker
heap limit to disguise process RSS, measuring a warm daemon instead of fresh
processes, deleting integrity work without replacing its consumed-byte proof,
adding a network fallback, or measuring only a library import while claiming
installed CLI fitness.

## Common runtime observation contract

Unit `006/00` creates `evals/salt-ai/doctor/runtimeFitness.mjs` and its focused
spec. It must reuse the existing pack, local-tarball install, fixture,
offline-guard, schema, parity, worker-mutation, and process-measurement helpers.
It must not shell around their exit codes or reimplement a second consumer
installer.

Keep four closed modes rather than growing a framework:

- `prepare` runs the existing exported pack validator exactly once in the
  Linux Node 24 build job, creates the portable candidate transport and its
  one shared consumer lock, and writes one sanitized pack-validation receipt;
- `observe` runs one host and writes one sanitized observation;
- `verify-candidate` runs all functional packed checks while capturing (but not
  deciding from) local performance, so Unit `006/01` can prove semantics even
  if the candidate will later receive a legitimate runtime RETIRE result; and
- `decide` consumes the exact required host observations, recomputes every
  derivation, and emits the one registered decision line.

Every invocation requires `--unit`. `prepare`, `observe`, and `decide` accept
only `006/00` or `006/02`; `verify-candidate` accepts only `006/01`. The unit is
embedded in every receipt and must match all other inputs and the emitted
decision. `decide` requires exactly one `--pack-validation <path>` and exactly
three `--observation <path>` arguments; missing, duplicate, or extra inputs are
invalid invocation.

`decide` writes exactly one LF-terminated compact JSON object to stdout and
diagnostics only to stderr. Exit `0` means it emitted one registered result,
including RETIRE or DEFER; `2` means invalid invocation or missing input; `3`
means malformed/unknown data or an identity/digest contradiction; and `4`
means runner, fixture, child-process, or internal execution failure. `observe`
and `verify-candidate` write no decision object and return `0` only after
their closed outputs/checks complete. Any nonzero status or extra decision
stdout is STOP and never enters control.

Unit `006/00` decision stdout has exactly the keys `contract`, `unit`,
`result`, and `worker_concurrency_one_eligible`, in that order. The last
value is a boolean recomputed from the forced-worker rule. Unit `006/02`
stdout has exactly the first three keys. The activation-frozen validator does
not duplicate the observation parser or decision arithmetic. On Unit `006/00`
and `006/02` transition/final phases it hashes the committed runner, invokes
that exact runner against the committed pack-validation and three observation
paths from control, and requires byte-for-byte agreement between stdout,
control result, and the Unit `006/00` eligibility boolean. Unit `006/00`
