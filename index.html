salt-eval

A benchmark that tells the Salt team whether giving AI coding agents Salt context makes the UI they build better.

The problem

Salt is a design system. Teams increasingly ask AI coding agents (Claude Code, Cursor, Codex) to build Salt interfaces. Several groups are making things that are meant to help those agents: an MCP server, a CLI, a skill, docs bundled into the npm packages. Nobody can currently say whether any of them works, or what to fix when it doesn't.

What salt-eval is

A repeatable experiment. It gives an agent a realistic request ("add navigation down the left side"), lets it work in an isolated sandbox, then grades the app it produced with automated browser checks. Run the same requests under different arms, where an arm differs only in what Salt context the agent gets, and compare pass rates.

It exists to answer two questions:

  1. Does Salt context help agents produce better UI? Compare arms task by task, with a noise floor so a difference means something.
  2. When it doesn't, what should we improve? Trace every failed check to a cause: a guidance gap, unclear guidance, a retrieval miss, tool misuse, misinterpretation, a prior override, an implementation error, or an eval defect. Each cause points to a different fix.
In one sentence: salt-eval grades the UI an agent built, not the tool that helped it, so any context product can be compared on equal terms.
Where it stands: the harness runs tasks end to end as a prototype, on a cheap development model, with no added context. Product arms, the oracle arm, attribution and comparisons are designed but not built yet. See Status.

Why it exists

The rationale: what we decided, what we rejected, and the rules that keep the comparison fair.

Principles

  1. Tasks before infrastructure. The task bank is the product. Build only the harness the current tasks need.
  2. Every metric maps to a decision. If a number can't change what we do next, we don't report it.
  3. Grade outcomes, not imports. Importing Salt or using a token proves nothing. Rendered behaviour, composition and cited guidance do.
  4. Grade only what the request or Salt guidance states. If two Salt experts could disagree on a verdict, it isn't a check.
  5. The agent never sees the answers. Trials run outside the repository. Held-out tasks and outputs never enter git.
  6. Read transcripts before trusting numbers. A score tells you which transcripts to read, not what happened.
  7. Change one thing at a time, and report every difference with its noise floor.

What it is not

  • Not a contract test for any one product. The MCP server's own evals stay with the MCP.
  • Not a model leaderboard, and not a single "Salt compliance" score.
  • Not a merge gate for Salt pull requests, until its numbers earn that.
  • Not about migration from other UI to Salt. That needs visual regression and is out of scope. Work types are create, extend and fix.

Fairness rules

These make it an experiment rather than a demo. Where a rule can be checked before a run, the launcher refuses rather than warns: inexact pins, a loosened network or verifier, instruction files in the image. Some are checked after the agent runs and fail the trial as a harness failure: pins, model, request and agent configuration. The comparison, statistics and split rules (marked planned) have no code behind them yet, because there are no comparisons yet.

RuleIn practice
One variable per comparisonAgent version, harness, gateway, model, Salt versions, task version and starting tree are recorded in pins.json for every trial. The harness commit carries a flag for uncommitted changes, and DeepSeek's model, which has no exact identifier, is pinned by name and reported display name.
Same agent and model for every armA product comparison never changes the model. Planned; the measured agent and model are still to be chosen.
The agent never sees the answersSingle-commit starting points; checks and reference solutions never enter the sandbox; the image is scanned for stray instruction files.

Decisions on record

Every trial so far is plumbing or harness development: Claude Code on DeepSeek, which isn't a model Salt consumers use. ADR 0003 allows three exceptions for that (no spend cap, no exact model pin, the all-ports network gap) that don't hold for measured runs.

Five architecture decision records (ADRs) live in salt-eval/docs/adr/. Each lists what was considered and what would make us revisit it.

Vocabulary

The terms used in the code, the docs and conversation. Use them exactly.

The full glossary is salt-eval/CONTEXT.md. This is the part you need to follow everything else, grouped by when you meet it.

What is being tested

TermMeaning
TaskOne frontend request, the starting point it runs from, the checks that grade it and the Salt guidance it depends on.
RequestThe message the agent receives, written as a product engineer or designer would ask. In Harbor it is instruction.md.
Starting pointThe frozen app a task begins from: source, locked dependencies, a single-commit git history.
Work typeCreate new UI, extend existing Salt UI, or fix Salt misuse.
FidelityPrototype or production. It limits what checks may penalise: placeholder links are fine in a prototype.
Decision typeThe kind of Salt decision a task turns on: setup and integration, component choice, composition, pattern, foundation, accessibility, content, API currency.
Guidance anchorA pointer from a check or rubric item to the passage of Salt guidance (docs, API types, deprecation notices) that justifies it, or an explicit "none". A "none" is a guidance gap.

What it is tested with

TermMeaning
AgentAn agent program (such as Claude Code) plus a model and its settings.
Context productA named, versioned way of delivering Salt guidance: an MCP server, a skill, bundled docs, a CLI, the Salt website, a DESIGN.md file.
ArmOne complete configuration trials run under: the agent, Salt version and the context products enabled. Arms in a comparison differ in exactly one thing.
Baseline armThe arm everything is measured against. "No context" still includes whatever the installed packages ship, such as types and CHANGELOG.md. Every baseline states what it includes.
Oracle armDiagnostic only: baseline plus the anchored passages pasted into the request. It shows the ceiling when retrieval is perfect. It is not a product, and not Harbor's "oracle agent".
Model gatewayThe service outside every sandbox that all model calls pass through. It holds provider keys and logs what reached the model.
PinsThe versions and hashes that make a trial reproducible. Written to pins.json.

What happens in a run

TermMeaning
TrialOne attempt by one arm at one task, from a fresh copy of the starting point.
SandboxThe isolated container a trial runs in. Nothing from the host reaches it unless the arm attaches it (with one known network gap, see How a trial runs).
Workspace → outputThe copy of the starting point the agent edits. When the trial ends it becomes the output: the diff plus the built app.
Transcript / traceThe raw record in the agent's own format / the normalised record: messages, tool calls with full results, commands, tokens.
Harness failureThe trial went wrong because of salt-eval or what it depends on (sandbox, gateway, provider). It says nothing about the agent, and is never counted. A harness failure wins over an agent failure.
Agent failureThe agent, correctly set up, ran out of time, context or output tokens, or refused.

How grading speaks

TermMeaning
CheckAn automated pass/fail test of one property of an output. Required checks decide task pass; diagnostic ones explain failures.
GateThe required check an output must pass before anything else is graded (C1 in task 1): it builds, and every page renders with no uncaught or console error. If it fails, every other check is unscorable.
Verdictpass, fail, unscorable (grading couldn't decide, never counts against the agent) or not applicable (a conditional check whose condition doesn't hold).
Task passEvery required check passes or is not applicable (and, once built, every required rubric item).
RouteOne of several valid ways Salt guidance allows a request to be met, such as VerticalNavigation or a stack of NavigationItems. Each route gets its own reference solution.
Reference solutionA known-good output used to prove checks pass valid work. Not the only acceptable answer.
Known-bad outputA realistic wrong output used to prove a check catches the mistake it targets.
Rubric itemA yes/no claim needing judgement, answered by a model judge only after it is shown to agree with human reviewers. Not built yet.
Eval defectA failure caused by salt-eval itself: ambiguous request, wrong check, broken starting point. Fixed, version-bumped and rescored, never counted.
One naming trap: Harbor calls a batch of trials a job and a single one a trial. salt-eval says run for the batch. Harbor's oracle agent replays a reference solution; salt-eval's oracle arm is something else entirely.

How a trial runs

From the command you type to a sealed record of what happened.

Three pieces on your machine

salt-eval run is a Python launcher wrapped around two things it does not implement:

  • Harbor runs the trial: it starts the sandbox from the image the launcher built, runs the agent, collects results, and runs the verifier.
  • A LiteLLM model gateway sits between the agent and the model provider. It holds the real API key and logs every request.

The launcher prepares everything, hands Harbor one task and one arm, then reads what Harbor wrote and decides the outcome. The launcher and Harbor run on the Mac. The sandbox and the gateway run as containers in OrbStack.

The steps of one run

Each named step appends a line to launcher.jsonl with what it observed and, if it failed, why. A refusal at any step still leaves a sealed record.

  1. lock Take a lock on the store so two runs can't collide. Remove a gateway container that a crashed run of the same store left behind; refuse one from anywhere else.
  2. pins.resolve Read the arm, task and gateway image. Refuse any inexact pin (including an undigested image or a Harbor version that doesn't match the lockfile) or any setting that loosens isolation. Only allow-listed task.toml keys and arm fields are accepted.
  3. docker.check Require macOS with OrbStack.
  4. image.build Build up to three layered images (below).
  5. image.scan Search the sandbox image for files Claude Code would read as instructions (CLAUDE.md, .mcp.json …). Refuse any outside the installed packages.
  6. gateway.start / health Read the DeepSeek key from the Keychain and start a fresh gateway with a new master key and a new token for this run.
  7. balance.before Ask DeepSeek directly (not through the gateway) for the balance and model list. Refuse below $1 or if the model can't be pinned.
  8. harbor.run Run Harbor with a scrubbed environment: only PATH, HOME, telemetry off and the gateway token.
  9. balance.after, gateway.stop Re-read balance, then stop the gateway so its log is complete.
  10. request.check The request the agent received (the first user message in the trajectory) must equal instruction.md byte for byte.
  11. pins.check Write pins.json; fail if what ran differs from what the arm asked for.
  12. model.check Fail if the model's display name changed mid-run or any response names another model.
  13. config.check Compare what Claude Code reported loading with a reviewed snapshot for its version. Whatever the snapshot says, web tools and MCP servers must be absent.
  14. secret.scan Once the gateway has started, fail if any of the run's three secrets (whole, or its last 20 characters) appears in the run's job, run or gateway records.
  15. seal Make the trial directory and runs/<id>/ read-only.

Between the checks and the scan, two unlogged steps copy the trial's gateway lines into the trial directory and classify the outcome: harness ok/failed and agent completed/failed/timed-out/not-run, from Harbor's result, the transcript, the gateway log and the verdicts. The reward number is never read.

Exit codes: 0 harness ok and agent completed (whether or not the task passed), 1 agent failed or timed out, 2 harness failure or refusal.

Three images

Harbor 0.24.0 can't swap a task's image per run, so the task names a moving tag (…:current) and the launcher builds each image with that tag before Harbor starts.

LayerContainsUsed by
Starting pointA Node image pinned by digest, the app, npm ci, one git commit with a fixed author and date, so its hash is identical on every rebuild.Base of the others
Agent layerStarting point plus Claude Code at the arm's exact version.The sandbox
Grader layerStarting point plus the graders project, Playwright, Chromium and axe-core. The app's node_modules moves aside so Harbor can upload the agent's output into /app.The verifier (Harbor adds the task's tests/ on top)

Isolation, in plain terms

  • The agent runs in a container, never on the host, so it can't read the repository or your user-level Claude config.
  • While it works, the only reachable host is the gateway. The agent runs as root, but the firewall rules are set by a sidecar whose network it shares; only the sidecar has NET_ADMIN, so the agent can't change them.
  • Real provider keys never enter the sandbox (the launcher and the gateway hold them). The agent holds a token valid only for this run's model, and the gateway redacts it from the log.
  • Checks and reference solutions are never uploaded to the sandbox.
  • For every graded task, grading happens afterwards in a different container with no network, so the agent can't tamper with the grader and leftovers can't affect the verdict.
Known gap: Harbor's allowlist works by host, not port, so the sandbox can reach every port on the Mac. That must be closed before the first baseline run. Each trial's pins.json records it honestly as "gateway host, all ports".

What gets recorded

Everything lives in a private store (SALT_EVAL_STORE, default ~/salt-eval-store/) outside git: runs.jsonl, runs/<id>/ (launcher log, run.json, job config, build, Harbor and gateway logs, DeepSeek model lists), gateway/<id>/requests.jsonl (every request as sent and as forwarded) and jobs/<id>/<trial>/ (Harbor's trial directory plus pins.json, status.json, the trial's gateway lines and a copy of the launcher log). The trial directory and runs/<id>/ are sealed; runs.jsonl stays appendable.

Tasks

The task bank is the product. This page covers what a good task is, how one is laid out, and task 1 end to end.

What makes a good Salt task

  1. It mirrors real Salt work. It reads like something a product team would ask an agent.
  2. It turns on 2–5 Salt decisions: which component, how to compose it, what guidance says about states, layout or accessibility. Not generic React or CSS puzzles.
  3. Two Salt experts would agree on every verdict. Everything graded is in the request or anchored to guidance.
  4. It accepts every valid solution by checking rendered properties, not one way of writing code.
  5. It respects its fidelity: a prototype never fails for placeholder links or mock data.
  6. It runs offline and repeatably.

Each task also states why it's hard in one line, naming how an agent's prior knowledge would go wrong. A decision where the agent would likely get it right anyway can't be the reason a task exists. This is how we avoid choosing tasks just because today's model fails them.

Anatomy

A task is a Harbor task directory (ADR 0004). Harbor never uploads the README to the sandbox, so the anatomy sits beside the request without reaching the agent.

tasks/<slug>/
  task.toml            Harbor settings + [metadata]: work_type, fidelity, specificity,
                       primary_decision_type, split (and variant_of)
  instruction.md       the request, byte for byte what the agent gets
  README.md            the anatomy, under 12 fixed headings (ADR 0004): why it's hard,
                       anchors, checks, rubric items, not checked, reference solutions,
                       known-bad outputs, what failures tell us, provenance …
  solution/            solve.sh + reference.patch (the primary reference solution)
  references/          one patch per other valid route
  known-bad/           one patch per realistic mistake
  tests/               Dockerfile, test.sh, checks.ts (the graders' input)

Reference solutions and known-bad outputs are patches against the starting point's single commit. Each header says what it is for: Route: on a reference, Targets: (and optionally Also fails:) on a known-bad output. git apply skips those lines.

Two starting points

NameWhat it is
empty-salt-appVite, React, Salt installed and a provider configured. Used for "create" tasks.
existing-salt-app"Client Portal": React Router, five sections, an app header, no navigation. Used for "extend" tasks. A task needing something more will start here with its own patch applied (decided; the mechanism isn't built yet).

Each has a README written as the app's own team would write it. It never mentions benchmarks or Salt how-to, and is always README.md, never AGENTS.md or CLAUDE.md, so the harness doesn't mistake it for an instruction file.

Worked example: task 1, left navigation

Extend · production · outcome-level · primary decision type: composition.

The request, verbatim: Our app has five sections: Overview, Accounts, Payments, Reports and Settings. There's no way to move between them. Add navigation down the left side that shows which section the user is on. We use React Router.

Why it's hard

Salt offers two routes to a left navigation. The newer, VerticalNavigation, is a compound component whose canonical composition nests VerticalNavigationItemContent around each trigger. No prose says it is required, only examples show it. An agent that leaves it out gets code that typechecks and renders, but each trigger's click area then covers the whole list, so clicking any item opens the last section.

Checks

IdLayerProperty
C1gateBuild passes; every section renders with no uncaught or console error
C2behaviourClicking "Payments" at the centre of its item shows the Payments page without a full reload
C3behaviourThe Payments item has aria-current="page", and no other item does
C4structureThe five items are rendered by Salt navigation components, not a hand-built list
C5structureThe nav has an accessible name (if VerticalNavigation is used)
C6structureEvery trigger sits inside an item-content wrapper (if VerticalNavigation is used)
C7structureThe navigation runs down the left side at 1280 × 720
C8behaviourSalt actually draws Payments active, and no other (if Payments is in a Salt navigation component)
D1structure (diagnostic)Which route was taken: vertical-navigation, navigation-item or other

C5 and C6 return not applicable on the other route, and C8 on a navigation not built from Salt components, so neither route is penalised. C8 was added after the first real trials: React Router's NavLink sets aria-current itself, so an output with no active prop passed C3 while showing nothing highlighted. C3 was too weak, the task went to version 2, and the three earlier trials were regraded for free.

The fixtures that prove the checks

Two reference solutions (one per route) and seven known-bad outputs, each aimed at one mistake: a full-page-reload link, no active item, NavLink with no active, a hand-built list, an unnamed nav, triggers without the content wrapper, and a horizontal header. Each known-bad's header names the check it Targets: and, on an Also fails: line, any other required checks the same mistake breaks. salt-eval test-checks grades all of these plus the untouched starting point and fails if any gets a verdict it shouldn't.

Decision types: how the bank gets its spread

Where Salt guidance lives decides what a failure points at. The first bank of about 30 tasks aims for a target spread.

Decision typeTargetA failure usually points to
Setup and integration3Getting-started docs, how context products read a project
Component choice5Retrieval: search terms, aliases, cross-links
Composition5Rules shown only in examples
Pattern5Pattern pages
Foundation3Token guidance, lint rules
Accessibility3Accessibility pages, component defaults
Content2Content guidance (thin)
API currency4Deprecation mappings, codemods

Writing tasks is itself a result: every anchor marked "none" and every unclear passage goes on the guidance issues list (G1–G24 so far). It is meant for the Salt docs owners as a first result that doesn't depend on any agent run.

Grading and attribution

How an output gets verdicts, and how a failure gets a cause.

Layers, cheapest first

LayerQuestionHowStatus
PlumbingDid the trial run properly?Exit status, timeouts, API errorsbuilt
GateCan the output be graded?Build, render every route, no uncaught or console errorbuilt
Behaviour and structureDoes the UI do what was asked, the Salt way?Playwright on the built app: interactions, roles, names, rendered salt* classes (axe-core is installed but no check uses it yet)built
SourceWhat only code showsDeprecated or nonexistent APIs from pinned types, files changed outside scope. (The typecheck already runs in the gate, as part of npm run build.)not yet
RubricWhat checks can't decideA model judge, validated against human labelsnot yet

If plumbing or the gate fails, nothing else runs. After that every check runs on every gradable output so attribution sees all failures. Prefer behaviour checks to source checks: they accept any implementation that produces the right result.

Seven rules for writing a check

  1. One property per check, named for the property, not the implementation.
  2. Justify it with the request or a guidance anchor. A check is required only if its justification rules out the alternatives it fails; guidance that recommends one option without ruling out others supports only a diagnostic check.
  3. An anchor of "none" makes the check diagnostic, and goes on the guidance issues list.
  4. Prove it: it passes the reference solution and fails the known-bad output it targets.
  5. Allow every valid route; make route-specific checks conditional.
  6. Respect fidelity; never check what "Not checked" excludes.
  7. Read deprecations and exports from the pinned version's types, not a hand-kept list.

How the verifier works

After the agent stops, Harbor starts a separate container with no network, uploads the agent's workspace into /app, and runs the graders:

  1. Copy the workspace, link the starting point's installed packages and run npm run build (60 s limit).
  2. Serve dist/ on localhost, falling back to index.html for client-side routes.
  3. Open each route in headless Chromium. A route fails the gate on an uncaught error or a console error, because React Router swallows render errors and only logs them.
  4. If the gate passed, run each check on a fresh page. A timeout is a fail; any other error is the grader's, so unscorable.
  5. Write verdicts.json with each check's verdict and evidence, plus task pass.

If a grader crashes or writes no verdicts, that is a harness failure, not an agent failure. Unscorable never counts against the agent: after a passed gate it makes the trial a harness failure. A failed gate is different: every other check is unscorable, and the task fails.

Testing the tests

salt-eval test-checks tasks/left-navigation grades every reference solution, every known-bad output and the untouched starting point, no model needed, about two minutes. Task 1's output:

output                             C1    C2    C3    C4    C5    C6    C7    C8    D1
solution/reference.patch           pass  pass  pass  pass  pass  pass  pass  pass  vertical-navigation
references/navigation-item.patch   pass  pass  pass  pass  n/a   n/a   pass  pass  navigation-item
known-bad/full-reload.patch        pass  fail  pass  pass  pass  pass  pass  pass  vertical-navigation
known-bad/no-item-content.patch    pass  fail  pass  pass  pass  fail  pass  fail  vertical-navigation
the starting point                 pass  fail  fail  fail  n/a   n/a   fail  fail  other

(Excerpt; an unexpected verdict is marked ! with the reason under the table.) A reference must pass every required check or be not applicable, and D1 must record the route its Route: line names. A known-bad must fail its Targets: check and every check on its Also fails: line, and nothing else. The starting point must pass the gate and fail, or be not applicable on, every other required check, with at least one fail. Diagnostic checks aren't compared. This catches checks that are too weak or too narrow before an agent is paid for.

salt-eval regrade <trial> reruns the current checks on a stored output with no agent and no model, in under a minute once the images are built. When a check is fixed, old trials are rescored instead of rerun.

Failure attribution

For each failed required check, walk these steps in order. The first match wins.

  1. Is salt-eval at fault? → eval defect. Fix, version the task, rescore, never count.
  2. Right intent, broken code? → implementation error. (A Salt export or prop that doesn't exist is a knowledge failure: continue.)
  3. Is the anchor "none"? → guidance gap.
  4. Did the anchored passage reach the agent? Search the trace's tool results, file reads and fetched pages (and the gateway's request log) for its text ("exposure").
    • No, because the agent misused a context product → tool misuse
    • No, otherwise → retrieval miss (record whether it never looked or looked and wasn't given it)
    • Yes, but the output follows an older or foreign convention → prior override
    • Yes, otherwise → misinterpretation
  5. Split misinterpretation with the oracle arm. If the oracle (passage in the request) fails too, the passage itself doesn't communicate → unclear guidance. If it passes, the passage works when prominent, and the product's presentation is the suspect.

An attribution is a hypothesis for the next experiment, not a proven root cause.

The anchor scorecard

One row per guidance passage across a run: exposure rate, pass rate when exposed, pass rate when not, oracle pass rate, main attribution. It turns numbers into the next change:

PatternWhat to change
Low exposure, high pass when exposedRetrieval: search terms, aliases, tool descriptions
High exposure, low pass when exposed, high oraclePresentation: put the rule earlier, shorten the example
Low oracle pass rateThe passage itself, or the component (a dev warning, simpler composition)
High pass when not exposedThe model already knows this
Anchor "none"Write the guidance, then promote the check to required

What is never reported

Salt import counts, token references, lint counts, tool calls, tokens or time as a quality win, a weighted "compliance score", 1–10 judge ratings, and percentages without task counts and intervals. Each one rewards the wrong thing, hides which decision failed, or can't be told apart from noise.

Running it

What you need, the four commands, and how to read what comes back.

A proof of concept, set up for local development. salt-eval is tightly coupled to one developer's machine today: macOS with OrbStack, a model key in the Keychain, a model gateway started per run, and a results folder in your home directory. That is deliberate for a proof of concept, and it is acknowledged that a real deployment needs its own design: where trials run, how secrets arrive, a shared gateway and results store. See Status.

Prerequisites

  • macOS with OrbStack (orb start if docker info fails). Other platforms are refused for now.
  • uv at exactly 0.10.9 (pinned in pyproject.toml). Install: curl -LsSf https://astral.sh/uv/0.10.9/install.sh | sh.
  • A DeepSeek API key in the Keychain item salt-eval-deepseek: security add-generic-password -a "$USER" -s salt-eval-deepseek -w. Only needed for run.

You do not set up Python. The first uv run creates the environment and installs Harbor 0.24.0 from the lockfile.

Commands

Run from the salt-eval/ folder.

CommandWhat it doesNeeds
uv run pytestThe harness's own tests, the task layout and the starting points. About 380 tests.Nothing (no Docker, no model)
uv run salt-eval test-checks tasks/left-navigationGrades every reference, known-bad output and the untouched starting point; compares verdicts to expectations. Exits 1 if any output gets a verdict it shouldn't.Docker
uv run salt-eval run --arm claude-code-deepseek-flash tasks/left-navigationOne real trial: agent in a sandbox, then graded. A few cents.Docker and the DeepSeek key
uv run salt-eval regrade <trial directory>Regrades a stored trial with the current checks into a new trial directory; the original is never changed.Docker
uv run salt-eval serve <trial directory>Builds a trial's output with no network and serves it at http://127.0.0.1:4173 so you can look at it (--port to change).Docker

The plumbing trial (plumbing-trial in place of the task path) is a throwaway request that proves the harness works end to end. It grades nothing and never counts.

Reading a result

salt-eval: run left-navigation-<timestamp>: harness ok, agent completed, exit 0
salt-eval: task pass: yes; C1 pass, C2 pass, ... C8 pass, D1 vertical-navigation
salt-eval: trial directory …
salt-eval: run records …

(Abridged; any refusal or failure reasons print first, one line each.)

  • harness ok / failed: did salt-eval itself behave? A failure here means the trial says nothing about the agent.
  • agent completed / failed / timed-out / not-run: did the agent finish? not-run means the run stopped before the agent started.
  • task pass: every required check passed or was not applicable. A failed task still exits 0: the exit code is about the harness and the agent, not the task.
  • D1 shows the route taken rather than a verdict.

Exit codes: 0 harness ok and agent completed, 1 agent failed or timed out, 2 harness failure or refusal.

  runs.jsonl                         one line per invocation
  run.lock                           held while a run is in progress
  runs/<run id>/launcher.jsonl       one line per step: what it observed, why it failed
  runs/<run id>/                    also run.json, build/Harbor/gateway logs
  gateway/<run id>/requests.jsonl    every model request, as sent and as forwarded
  jobs/<run id>/<trial>/
     pins.json  status.json          what was pinned; the outcome
     gateway/  launcher.jsonl        this trial's gateway lines; a copy of the launcher log
     agent/ artifacts/ verifier/     transcript, trajectory; workspace and diff; verdicts.json

Once a run ends, its trial directory and runs/<run id>/ are read-only. To experiment without touching your store: SALT_EVAL_STORE=$(mktemp -d) uv run salt-eval run ….

When something is refused

Refusals are deliberate. Loosening a task's network mode, naming an unpinned version, adding an unlisted task.toml key or a verifier that isn't the task's own grader layer each stop the run at pins.resolve with a message naming the rule, before Docker builds anything. The first trial on any new Claude Code version fails at config.check on purpose, and writes what it observed so a human can review and commit a snapshot. The README shows how to trigger each refusal that can be triggered by hand and which tests cover the rest; the rules themselves are in src/salt_eval/refusals.py.

Status and next steps

Where salt-eval stands, the question that matters most now, and the phases ahead.

Where we are

We are building out the question bank: the Salt tasks the benchmark grades agents on.

Everything so far runs outside J.P. Morgan, on a development model no Salt consumer uses, with no Salt context products attached.

Top priority: what can we mirror inside J.P. Morgan?

This comes before any other harness work. salt-eval's numbers only matter if trials run where Salt's consumers work, with the agents and models they actually use. The prototype was built on a laptop against an outside model provider. Until we know which of its parts can be reproduced in J.P. Morgan infrastructure, building more of it risks building the wrong thing.

For each part of the prototype, we need to find out whether it can run inside as it is, needs an internal substitute, or is blocked:

PartIn the prototypeWhat we need to find out
SandboxesContainers on a MacCan we run isolated containers with their network locked down?
Trial runnerHarbor, an open-source toolCan it be installed and run internally, or do we need an equivalent?
Agents and modelsClaude Code on an outside modelWhich agent programs and models are approved and used by Salt consumers, and can their traffic go through a gateway we control and log?
Salt and its packagesInstalled from public npmCan every package a task needs be installed from the internal registry, offline?
Context productsNone attached yetCan the MCP server, skill, CLI and bundled docs be attached to an internal agent the way consumers attach them?
GradingA headless browser, no networkCan a headless browser run in the internal environment?
Results storeA folder on a laptopWhere can transcripts, outputs and held-back tasks live, and who can see them?

The outcome is a map of what runs where. It decides the shape of everything in the architecture track below.

Roadmap

Two tracks move together: the architecture that runs trials, and the question bank of tasks it runs. Each phase ends when both tracks have reached its "done when", and each phase answers a bigger question than the one before.

1. Prove the method2. Bring it inside3. First answer4. Compare and improve

We are here: phase 1 is complete and phase 2 starts with the J.P. Morgan infrastructure map. Seed tasks continue to be written on paper alongside it, so the bank is ready when the harness is.

Next steps

  1. Map J.P. Morgan infrastructure against the table above, with the teams that own each part.
  2. Keep the harness as it is until the map exists. The prototype has done its job. New harness work waits for what the map says can run inside.
  3. Keep writing seed tasks. Tasks don't depend on where they run, and writing them already finds gaps in Salt guidance (24 so far).

Open questions

  • Which agent programs and models do Salt consumers inside J.P. Morgan use? That decides what gets measured.
  • Can model traffic go through a gateway we control, so we have a record of exactly what each agent saw?
  • Where should results and held-back tasks live, and who owns that store?
  • What does "no added context" mean inside? Salt's installed packages already teach agents some answers (the shipped changelog shows how to compose task 1's navigation), and every baseline has to state what it includes.
