## Why this matters

The release gates catch stale generated bytes, but the current source still has
two user-visible correctness defects and several narrower contract gaps:

1. the server advertises pre-2025-06 MCP revisions whose official tool-result
   schemas reject the `resource_link` blocks returned by every non-empty search;
2. a QA story currently becomes published Splitter token-applicability evidence;
3. project-controlled dependency strings can be interpolated into top-level
   limitations that consumers are encouraged to trust;
4. review results say no repository state was observed even when a retained or
   fresh project snapshot supplied policy and installed-version facts;
5. legal long roots can create a context handle larger than its own public
   schema accepts, and lockfile detection reads up to 8 MiB per marker merely to
   prove presence;
6. the Date package verifier is absent from PR CI, tests the repository dist
   rather than an installed tarball, and permits dead workspace metadata and
   unnecessarily mandatory peers; and
7. the current MCP generated/package bytes predate the latest Date source.

The fixes should preserve the product's deliberately small public surface:
three tools, one resource, two resource templates, read-only operation, and
dual ESM/CJS Date output.

## Steps

### Step 1: Make the advertised MCP protocol set truthful

Choose the smallest supported contract: remove `2025-03-26`, `2024-11-05`, and
`2024-10-07` from `SALT_MCP_SUPPORTED_LEGACY_PROTOCOL_VERSIONS`, leaving the
current protocol plus `2025-11-25` and `2025-06-18`. Do not retain an old
revision merely because SDK initialization succeeds; the complete non-empty
tool result must satisfy that revision's CallToolResult schema.

Add a table-driven real-transport test for every advertised revision. For each
revision, negotiate exactly that version, call `search_salt` with a query known
to return at least one match, and validate the complete result against the
revision-specific SDK/official schema. Also call one non-search tool that emits
evidence links. Assert unadvertised older revisions are absent from metadata and
consumer smoke configuration.

Update README compatibility language to list the exact supported revisions and
state that resource links require the 2025-06 protocol shape.

**STOP:** if a supported consumer contract explicitly requires a pre-2025-06
revision, do not narrow it and do not ship a partial fallback. Stop and create a
separate protocol-aware projection design that proves text/structured evidence,
budgets, and schemas for each older version.

### Step 2: Remove test/story contamination from token applicability

First add a characterization fixture with the same token in a production
implementation file and in neighboring `*.spec.*`, `*.test.*`, `__tests__`, and
story/QA files. Run it through `linkTokensToComponents`, the real registry build,
and V2 normalization. Assert only the production occurrence contributes
`applies_to`.

Add one shared, explicit test/story exclusion set for directory-valued
implementation scans and use it in the token scanner. Do not blindly copy
component scanner exclusions such as `*.css.ts`; characterize production CSS
and CSS-in-TS first and retain formats that carry real implementation tokens.
Keep direct-file component sources readable.

Regenerate a temporary catalog and assert the affected token still applies to
Progress but no longer to Splitter. Prove the source and normalized V2 record,
not a handcrafted post-normalization object. Plan 005 will later decide whether
the now-unused QA/test bytes can leave the canonical inventory.

### Step 3: Separate trusted diagnostics from project-controlled strings

Replace free-form interpolated installation limitations with stable diagnostic
codes and bounded templates. Preserve useful raw package names, ranges, and
resolved versions only inside an explicitly labelled
`untrusted_project_data` diagnostic collection with:

- `classification: untrusted_project_data`;
- `instruction_authority: none`;
- a stable code;
- bounded typed parameters; and
- deterministic truncation/omission counts.

Top-level `limitations` may contain only repository-authored fixed strings or
stable code-derived templates with no project-controlled interpolation. Update
the strict output schema and text fallback consistently; never copy raw values
back into an error message or summary.

Extend `projectInspectionTrustBoundaries.spec.ts` with adversarial dependency
keys/ranges containing instruction-like text, control-looking markup, Unicode,
and maximum-length values. Through a real MCP call, prove raw values are present
only under the labelled envelope and absent from the trusted projection,
top-level limitations, thrown errors, and text content. Preserve existing byte
and package-count limits.

### Step 4: Report review context honestly

Keep `scope.kind = submitted_text_only`: only submitted artifact bytes are
analyzed. Add an orthogonal exact context-source field with these values:

- `none`;
- `caller_package_versions`;
- `retained_project_snapshot`;
- `fresh_project_inspection`.

Pass this discriminator from `toolDefinitions.ts` into `reviewSaltCode` instead
of inferring it from the eventual policy object. Adjust limitations so they say
unsubmitted source was not analyzed while accurately acknowledging when
authorized project policy/version facts were read or reused. Provenance digests
remain exact and nullable as today.

Add real-transport tests for all four modes. Each test must assert the context
source, digest behavior, version/policy effect, and the unchanged
`submitted_text_only` artifact scope. A retained snapshot test must still work
after its policy file is removed; a fresh-root test must observe a permitted
change.

### Step 5: Make context handles fixed-size opaque cache capabilities

Stop encoding `root_dir` in the public handle. Generate a fixed-size,
cryptographically random base64url token when a snapshot is inserted and bind
that token to the exact root/context digest inside the existing bounded LRU.
Parsing should validate prefix/shape only; lookup returns the bound snapshot and
then performs the existing authorization/digest checks.

Eviction, byte/count limits, denial behavior, and process-local semantics remain
unchanged. Do not persist handles, make them bearer credentials across servers,
or expose root paths through a reversible token. If a snapshot is replaced,
old tokens must not resolve to new contents.

Tests must cover a maximum accepted multibyte root, constant handle length,
round-trip reuse, eviction, malformed/forged tokens, old-token invalidation,
and reauthorization after the allowed-root policy changes. Cross the real
inspect-to-review transport path.

### Step 6: Probe package-manager markers without reading contents

Add a contained metadata-only file probe beside `readBoundedProjectFile`. It
must open with no-follow semantics, require a single-link regular file, verify
lexical/real containment and portable spelling, compare descriptor identity to
the named path, and return the existing absent/invalid reason vocabulary. It
must not allocate from or read file size.

Use that helper only for package-manager marker presence. JSON, YAML, policy,
manifest, and tsconfig readers continue through bounded content reads.

Tests must prove a regular marker larger than 8 MiB is detected without reading
its bytes; linked, hard-linked, directory, outside-root, and path-rebound markers
remain invalid; and no marker content appears in diagnostics.
