# Decision types

A task's difficulty comes from two to five Salt decisions (see "What makes a good Salt task" in [tasks.md](./tasks.md)). This page sorts those decisions into eight decision types, sets out the tests that separate a good task from a plausible one and lists researched decision points to build tasks from. It assumes the anatomy and acceptance checklist in tasks.md.

Anchors are quoted from `@salt-ds/core` 1.72.0. Paths are relative to `site/docs/` unless they start with `packages/` or `site/src/`. Re-check an anchor against the pinned version before a task uses it.

## The eight decision types

| Decision type         | The agent decides                                            | Guidance it draws on                                                          | A failure usually points to                                                    |
| --------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Setup and integration | How Salt is installed, themed and wired into the app's stack | Getting-started pages, provider pages, setup sections of packages beyond core | Getting-started docs, and how context products read a project                  |
| Component choice      | Which Salt component does the job, or that none does         | "When to use" and "When not to use" on usage pages                            | Retrieval: search terms, aliases and cross-links between near neighbors        |
| Composition           | How a compound component's parts nest                        | Examples and composition prose on component pages                             | Example-only rules, composition data in context products, development warnings |
| Pattern               | How several components combine for one job                   | Pattern pages                                                                 | Pattern pages, and whether a component query leads to them                     |
| Foundation            | Tokens, spacing, density, modes, typography and layout       | Foundation and theme pages, layout component pages                            | Token guidance and lint rules                                                  |
| Accessibility         | What the consumer must add for an accessible result          | Component accessibility pages                                                 | Accessibility pages, or the component's defaults                               |
| Content               | Labels, casing and messages                                  | "Content" sections of usage pages, case rules in typography                   | Content guidance, which is thin                                                |
| API currency          | The current API at the pinned version                        | Pinned types, the changelog, lab and core exports                             | Deprecation mappings, codemods and lint rules                                  |

The types split Salt guidance by where it lives, so each type's failures point to a different part of the guidance and a different kind of fix. Between them they cover every kind of Salt guidance listed in [CONTEXT.md](../CONTEXT.md).

### How the types combine

- **One primary type per task.** It's the type of the decision "Why it's hard" leads with, which most required checks test. A task's other decisions can be of any type: a form in a dialog is a pattern task that also has composition, accessibility and content decisions.
- **Spread primary types across the bank.** The table below gives starting targets for the first bank of about 30 tasks. Content and accessibility decisions fit inside tasks of other types, so they need fewer tasks of their own. Revise the targets once the Phase 3 pilot shows where agents fail.
- **Fill the gaps the worked examples leave.** The worked examples in tasks.md are composition (1), pattern (2 and 3) and a fix task whose seeded defects span four types (4). The remaining seed tasks should take component choice, setup and API currency as their primary types: their checks are deterministic and the agent's prior is most likely to be wrong.

| Decision type         | Primary in first bank | Work types that suit it                            |
| --------------------- | --------------------- | -------------------------------------------------- |
| Setup and integration | 3                     | Migrate; extend with a capability that needs setup |
| Component choice      | 5                     | Create, extend, migrate                            |
| Composition           | 5                     | All four                                           |
| Pattern               | 5                     | Create, extend                                     |
| Foundation            | 3                     | Extend, fix                                        |
| Accessibility         | 3                     | Extend, fix                                        |
| Content               | 2                     | Extend                                             |
| API currency          | 4                     | Extend next to legacy code, fix                    |

## What separates a good task from a plausible one

The acceptance checklist in tasks.md sets the bar every task meets. These six tests catch what most often slips past it. They come from audits of published coding benchmarks, which kept finding tasks an agent could pass without the capability under test, or fail despite having it. The Agentic Benchmark Checklist ([Zhu et al., 2025](https://arxiv.org/abs/2507.02825)) states the goal: "a task should be solvable if and only if the agent possesses the target capability." For salt-eval, that capability is applying Salt guidance.

1. **It names how the prior goes wrong.** For each decision in "Why it's hard", say why an agent without Salt guidance would likely choose differently:

   - another library gives the name a different meaning: an MUI `Drawer` can stay open beside the page, but in Salt "Drawers are always modal";
   - the API is newer than most training data: `LinkButton` arrived in 1.71.0;
   - the API changed: Button `variant` gave way to `appearance` and `sentiment` in 1.36.0;
   - the rule is shown only in an example, like `VerticalNavigationItemContent`;
   - near neighbors split one job, like `Banner` and `Toast`;
   - the rule spans components, like no card inside another card.

   A decision with no such reason will probably pass on the baseline arm, so it can't be the reason a task exists. It still earns a place as a secondary decision, because it shows when a context product makes agents worse at something they already knew. Documentation retrieval has done exactly that: with an imperfect retriever, valid calls to well-known APIs dropped by 39 percentage points ([Jain et al., 2024](https://arxiv.org/abs/2407.09726)).

2. **The request states the fact the guidance turns on.** Salt's rules key on product facts: how many options there are, whether a setting applies immediately, whether a message concerns the user's current task, whether the page must stay usable while a panel is open. The request must state that fact in product language. Without it, the decision isn't forced and the check fails work two experts would accept. Each decision point below names its key fact. Keep away from the edges of Salt's thresholds: radio button and dropdown usage don't settle exactly five or exactly ten options.

3. **Every requirement in the request has a check.** tasks.md requires every check to trace back to the request or an anchor. The reverse matters as much. Terminal-Bench asks for "a clear instruction and robust verifier such that a solution passes verification if and only if it successfully completes the instruction" ([contributing guide](https://github.com/harbor-framework/terminal-bench/blob/main/CONTRIBUTING.md)). A requirement nothing checks rewards agents that skip it. If it isn't worth a check, cut it from the request.

4. **The checks are proven from both sides.** Besides the reference solution and known-bad outputs, two more outputs test the checks before any agent runs. The untouched starting point must fail every task-specific check: on τ-bench's airline tasks, an agent that returned empty responses scored 38% and beat a GPT-4o agent ([Zhu et al., 2025](https://arxiv.org/abs/2507.02825)). Where the request allows more than one route, a second reference solution that takes the other route must pass. Then review each check for being narrow (it rejects valid work) or wide (it tests something neither the request nor the guidance asks for). OpenAI's audit of SWE-bench Verified found narrow tests in 35.5% of the tasks it examined and wide tests in 18.8% ([OpenAI, 2026](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)).

5. **Trial failures land on the named decisions.** Once trials run, read where they fail. A failure that "Why it's hard" doesn't name, such as build tooling, data wiring or an unrelated layout bug, means the task is hard for the wrong reason. METR's task guide: "Tasks shouldn't be difficult for incidental reasons" ([METR](https://taskdev.metr.org/desiderata/)). Move that work into the starting point.

6. **The code beside the edit is chosen on purpose.** Agents copy what's around them. In a study of line-level code completion with 2024-era models, models used a deprecated API in 70–90% of completions when the surrounding code used it, and in 9–18% when it used the replacement ([Wang et al., 2024](https://arxiv.org/abs/2406.09834)). For extend and fix tasks, record whether the code near the edit uses current Salt, older Salt or hand-built UI. Legacy surroundings make a useful paired task, but never an accidental one.

## Decision points by type

Each type below says what a good task of that type needs, then lists decision points. They're ranked by value: Salt's answer differs from a likely default, the passage settles it and the rendered page can show it. "Check" says whether the anchor supports a required check or only a diagnostic one, as defined under "Writing checks" in [grading.md](./grading.md). The request ideas are unvalidated candidates for Phase 1 and the first bank.

### Setup and integration

**A good setup task**

- Setup decisions exist only where the starting point hasn't made them: a non-Salt app being migrated, or a Salt app gaining a capability with its own setup, such as dates, client-side routing, a data grid or charts.
- Trials run offline, so preinstall every package the decision needs and serve fonts locally. The decision under test is the wiring. A font loaded from a CDN fails offline and turns a font check into a network check.
- Check outcomes, not import paths: a Salt token resolves, the font renders, a date can be typed and picked. Salt's own pages disagree on which theme CSS files to import (see "Guidance issues found while researching" below).
- The root `SaltProvider` writes its theme classes, `salt-density-<density>` and `data-mode` onto `<html>` (`packages/core/src/salt-provider/ThemeApplicator.tsx`). Checks can read them to confirm the provider is in place.

### Component choice

**A good choice task**

- Near neighbors go in one task so each is the other's contrast: a setting that applies at once beside one that's saved, an error on this page beside a background notification. An agent that reaches for one component everywhere fails one of the pair.
- Migrate tasks get choice decisions from foreign names that map to more than one Salt component. A persistent MUI `Drawer` becomes a Salt `SidePanel` or a border layout region, not a Salt `Drawer`. An MUI `Chip` becomes a `Pill` or a `Tag`, a `Snackbar` becomes a `Toast` or a `Banner` and a `Select` becomes a radio group, `Dropdown` or `ComboBox` depending on how many options it has.
- Where Salt has nothing for part of the job, the right output builds that part from Salt primitives and tokens. Including such a part shows whether a context product pushes agents to invent Salt APIs, which then fail the build gate.

### Composition

**A good composition task**

- Find each component by role and accessible name, then check its parts by the classes they render. That accepts the app's own wrapper components.
- Where a part must be a direct child, as card and overlay sections must, check that relation on the rendered page. A wrapper that breaks it fails, and that's the rule.
- Lab and core render the same root classes for `Tabs`, `Toolbar`, `Tooltray` and `ComboBox`. For these, add a source check that the import comes from `@salt-ds/core`.
- A rule shown only in an example can still justify a required check when experts agree on it, as in worked example 1, and it goes on the guidance issues list either way. These rules are where the oracle arm says most: if it fails too, the example doesn't get the rule across.

### Pattern

**A good pattern task**

- Pair contexts that flip a rule. The same form on a page and in a dialog flips button order. An agent that passes one and fails the other learned an order, not the rule.
- Several patterns predate the components that now do their job: breadcrumbs, vertical navigation and persistent dashboard panels. Accept both routes and record the one taken, as worked example 1 does.
- Some rules show only after time passes or state changes, like the ten-second limit on spinners. Build the delay or state into the starting point's stubs so a check can reach it without a backend.

### Foundation

**A good foundation task**

- The strongest foundation checks change the environment instead of reading the code. The request says the app has a dark mode and a compact layout, and the starting point provides the controls for both. After the agent finishes, the check switches both on through those controls and looks again. Styling built on Salt tokens follows; hex colors and fixed pixel sizes don't.
- No Salt passage rules out hand-written CSS layout, so "uses Salt layout components" stays diagnostic. It's a guidance gap only if maintainers agree Salt layouts are expected.
- Source scans for hex values or `--salt-palette-*` tokens explain a failed mode check, but stay diagnostic: the token pages describe Salt's own layers rather than rule on app code.

| ------------------------------------------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |

The purpose of the palette layer is to enable mode switching". `themes/design-tokens/how-to-read-tokens.mdx`: "Don’t choose a token just because its color looks right" | After the switch to dark mode, the custom element's colors change and axe-core reports no contrast violation           | Required, justified by the request; the token scan is diagnostic |
| Space and size custom UI with tokens       | The app has a compact layout | `foundations/spacing.mdx`: "Salt’s spacing system uses a base unit, `--salt-spacing-100`, which scales proportionally across all desktop densities". `foundations/size.mdx`: "Each size token responds to density"                                                                             | After the switch to high density, the custom element's gaps and heights shrink with the Salt components around it      | Required, justified by the request                               |

### Accessibility

**A good accessibility task**

- Test what Salt leaves to the consumer. Most Salt components set their own roles and focus behavior; the decision points below are documented exceptions that axe-core can't detect.
- Exercise the whole interaction: open and close, select and deselect, with the keyboard as well as the pointer, and check where focus goes at each step.

| Decision                               | Key fact the request states                    | Anchor                                                                                                                                                                                                                                      | Signal                                                                                        | Check                           |
| -------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------- |
| A banner's role matches its urgency    | Whether the message must interrupt the user    | `components/banner/accessibility.mdx`: "When using a banner to alert the user, apply `role="alert"`. When using a banner to notify the user, apply `role="status"`." `Banner` sets no role itself, while `Toast` always sets `role="alert"` | `saltBanner` has the matching role                                                            | Required                        |
| Destructive dialogs focus Cancel first | The action can't be undone                     | `components/dialog/accessibility.mdx`, "Focus sequence": "For dialogs with destructive interactions, the cancel button takes focus first."                                                                                                  | When the dialog opens, the focused element is its Cancel button                               | Required                        |
| Alert dialogs use `role="alertdialog"` | The dialog warns or reports an error           | `components/dialog/usage.mdx`: "For accessibility reasons, pass `role="alertdialog"` to the dialog component when rendering an alert dialog."                                                                                               | A `saltDialog` with a status has `role="alertdialog"`                                         | Required                        |
| Decorative icons are hidden            | An icon sits beside a visible label            | `components/icon/accessibility.mdx`: "If you're adding an icon for decorative purposes, pass `aria-hidden=”true”` to exclude its label from the screen reader." Salt icons ship a default `aria-label`, such as "add" on `AddIcon`          | The control's accessible name equals its visible label, with no icon name added               | Required                        |
| A skip link comes before a busy header | The header has navigation and utility controls | `patterns/app-header.mdx`: "precede those header components with a skip link." `components/skip-link/usage.mdx`: "Skip links should be the first focusable element"                                                                         | The first Tab press focuses `saltSkipLink`, and activating it moves focus to the main content | Required at production fidelity |

**Request ideas**

- "Let users delete a draft trade from its row. Deleting can't be undone, so make an accidental delete unlikely." Extend, production. Decisions: `role="alertdialog"` with a warning status, Cancel focused first, dialog button order, a verb on the confirm button.
- "Add search, notifications and a profile menu to the app header, which already has six sections." Extend, production. Decisions: a skip link, decorative icons hidden beside their labels, `Menu` for the profile actions.

### Content

**A good content task**

- Salt's content guidance lives in per-component "Content" sections and typography's case rules. Nothing cross-cutting covers error, empty-state or confirmation copy, so most content decisions ride inside tasks of other types, and every gap goes on the guidance issues list.
- Leave casing to the agent: write labels in the request as plain prose ("sections for overview, recent activity and documents"). A request that spells "Recent Activity" has already decided, and a check against it would be wide.
- Both documented themes uppercase button labels in CSS (`--salt-text-action-textTransform`), so the DOM text is whatever the agent typed. Compare button names case-insensitively.
- Use checks only for fixed strings, such as "OK", "click here" or a trailing ellipsis. Write everything else as a rubric item with its passage attached.

| Decision                                                | Key fact the request states                   | Anchor                                                                                                                                                                                                                                               | Signal                                                                                             | Check                              |
| ------------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------- |
| Buttons are labeled with verbs                          | What the action does                          | `components/button/usage.mdx`, "Content": "Always use verbs that emphasize the action the button carries out. For example, use **Create** instead of **Ok** to create a profile, or **Save**/**Discard** instead of **Yes**/**No** to save changes." | No button named "OK", "Yes" or "No"; a rubric item for the rest                                    | Required                           |
| Interface text is in sentence case                      | The request leaves casing open                | `foundations/typography.mdx`, "Sentence case": "Sentence case is mainly used for body copy, page titles, navigation, subheadings, form titles, field labels, and chart titles and text." "Title case is reserved for proper nouns and job titles"    | A rubric item: headings, labels, tabs and menu items are in sentence case, apart from proper nouns | Required                           |
| A menu item that needs more input ends with an ellipsis | One menu action asks the user for information | `components/menu/usage.mdx`: "Use an ellipsis at the end of a menu item label for actions that will require more information from the user to complete."                                                                                             | That item's label ends with "…" or "..."                                                           | Required                           |
| Link text names the destination                         | The page has a text link to another page      | `components/link/usage.mdx`, "Content": "Do not include the word “link” in the link text." and "Link text should accurately describe the linked content."                                                                                            | No link named "link", "here" or "click here"; a rubric item for the rest                           | Required                           |
| One date format in the label and helper text            | The field accepts a typed date                | `components/date-picker/usage.mdx`, "Best practices": "recommend a single acceptable date format in the form field label and helper text"                                                                                                            | A rubric item: the label or helper text names exactly one format                                   | Diagnostic: the passage recommends |

**Request idea**

- "Add an actions menu to each account row: rename, export to CSV and close account." Extend, production. Decisions: `Menu` rather than `Dropdown`, an ellipsis on the rename item because it asks for a name, sentence case. "Not checked" lists whether closing the account gets an ellipsis, since asking for confirmation isn't clearly asking for information.

### API currency

**A good API currency task**

- The strongest task is an extend task with legacy code beside the edit. The request asks for new UI next to code that uses an old form; the agent should write the current form and leave the old code alone. Pair it with the same task in current surroundings, and the gap between the two measures prior override directly.
- Rendered classes often can't see currency: a deprecated Button `variant` still renders `saltButton-solid`. Currency checks are source checks against the pinned types (see "Writing checks" in grading.md), and each one's known-bad output uses the old form.
- Package moves are the subtlest change. Lab's `FormField` and `Input` are the legacy components under core's names, and models confuse a deprecated API with its replacement most when little but the package changed ([Wang et al., 2024](https://arxiv.org/abs/2406.09834)).
- Choose APIs newer than likely training data on purpose, and record the version each arrived in: `Toggletip` 1.59.0, the current `Tabs` 1.61.0, `SidePanel` 1.62.0, `Tree` 1.63.0, core `Toolbar` 1.65.0, `MegaMenu` 1.66.0, `Breadcrumbs` and card sections 1.69.0, `LinkButton` 1.71.0.

Use `appearance` and `sentiment` instead."                                                                         | The source passes the deprecated prop              | Required                        |
