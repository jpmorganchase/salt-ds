Use this page as a short chooser, then follow the component usage pages for the
authoritative details.

## Start with user intent

- Trigger work in the current view: use [`Button`](/salt/components/button).
- Navigate between application or website destinations: use horizontal
  [`NavigationItem`](/salt/components/navigation-item) or, for new vertical
  navigation, [`VerticalNavigation`](/salt/components/vertical-navigation).
- Follow a destination within page content, such as a help article or download:
  use [`Link`](/salt/components/link).
- Switch between distinct content panels within the same page: use
  [`Tabs`](/salt/components/tabs).
- Show or hide related content: use a disclosure primitive such as
  [`Accordion`](/salt/components/accordion) or
  [`Collapsible`](/salt/components/collapsible).
- Structure a page or region: start with
  [layouts](/salt/components/layouts/index).
- Build a repeated multi-part flow: check [patterns](/salt/patterns/index)
  before inventing a new composition.

## Quick decision table

| User intent                                    | Prefer                                                                                                               | Main thing to avoid                                 |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| Trigger work                                   | [`Button`](/salt/components/button)                                                                                  | `Link` or custom link-like actions                  |
| Navigate across an app or site                 | [`NavigationItem`](/salt/components/navigation-item) or [`VerticalNavigation`](/salt/components/vertical-navigation) | Custom navigation that recreates covered behavior   |
| Follow an inline destination                   | [`Link`](/salt/components/link)                                                                                      | `Button` used as route or document navigation       |
| Switch distinct content panels                 | [`Tabs`](/salt/components/tabs)                                                                                      | Treating local panels as separate destinations      |
| Change the same records between List and Cards | [`ToggleButtonGroup`](/salt/components/toggle-button/usage#view-switching)                                           | Tabs used for presentation settings                 |
| Repeated multi-part flow                       | [Patterns](/salt/patterns/index)                                                                                     | ad hoc assemblies                                   |
| Arrange page or shell structure                | [Layouts](/salt/components/layouts/index)                                                                            | generic wrappers that add no value                  |
| Existing Salt screen                           | Salt primitives                                                                                                      | recreated native or role-based interactive elements |

## Common decisions

### Button or Link

- Use `Button` for actions such as save, apply, retry, or open dialog.
- Use `Link` for real destinations within page content, such as help articles
  or document downloads. For application navigation, use the navigation
  components below.

### Navigation or Tabs

- Use horizontal `NavigationItem` for application or website destinations,
  such as a header linking Overview, Team, and Settings. Use
  `VerticalNavigation` for new structured vertical navigation.
- Use `Tabs` for distinct content panels within the same page. The presence
  of a URL fragment alone does not decide the component: establish whether
  the user is navigating to a destination or switching a local panel.
- Preserve the application's routing owner. Follow the selected component's
  usage guidance for integrating its link with the existing router.

### Tabs or ToggleButtonGroup

Use `Tabs` for distinct panels such as Details and History. Use `ToggleButtonGroup`
for different presentations of the same records, such as List and Cards. Keep the
query, filters, sort and selected record in shared application state. Follow the
[view-switching guidance](/salt/components/toggle-button/usage#view-switching)
for selection, focus and the distinction from `SegmentedButtonGroup`.

### Radio buttons, checkboxes or a selectable list

Choose by single or multiple selection, whether the options should remain visible,
and whether typing would help users find an option. Use `RadioButtonGroup` for a
small, mutually exclusive set, `CheckboxGroup` for visible independent choices,
`ListBox` for an always-visible list, `Dropdown` for a popup and `ComboBox` when
filtering helps. Follow [Choosing a selection control](/salt/components/list-box/usage#choosing-a-selection-control)
for the full decision and application responsibilities.

### Component or pattern

- Derive the UI roles first: for example, content container, action,
  destination, selection control, status, layout region, or repeated flow.
- Check Salt component and pattern coverage for those roles before composing
  anything new. Start with a component when one element has clear semantics;
  start with a pattern when the job spans a repeated flow or page structure.
- Compose the selected Salt parts before writing CSS. Use tokens to customize
  or complement those parts, not to recreate their behavior or semantics from
  generic elements and custom roles.
- Create custom UI only for an actual coverage gap. State the missing role or
  behavior, keep that addition scoped to the gap, and do not duplicate an
  existing Salt primitive under a different name.

For example, a metric summary may lead to [`Card`](/salt/components/card) as
the content container. Use its documented `variant` and `accent` props for
hierarchy; if the whole region instead navigates or selects, consult the card
coverage for the corresponding existing Salt component before composing it.

### Salt primitive or custom wrapper

- Prefer the Salt primitive first.
- Add a wrapper only when it adds stable semantics, shared behavior, or a real
  domain API.
