## When to use

Use navigation to reach destinations such as pages, resources or sections within a page. Navigation controls can appear in the main navigation or within page content. Choose them according to the destination and the user’s task. When deciding on your application’s main navigation, it’s important to:

- Display navigation in websites or applications with two or more pages to indicate content hierarchy and help users orient themselves.
- Simplify your hierarchy to help users locate the information they want in the fewest clicks, to reduce the user's cognitive load.
- Label effectively with clear and concise label descriptions or visual cues, such as descriptive icons, to specify the destination a navigation item directs users to.

For responsive settings section navigation, use the [preferences dialog pattern](./preferences-dialog) with `VerticalNavigation`. Its narrow layout moves from categories to settings and provides Back to return to categories.

## When not to use

- When the task is primarily about completing a workflow, use Forms, Wizard, or Dialog instead of site navigation.
- When users switch between a flat set of distinct content panels on the same page, such as Details and History, use [`Tabs`](/salt/components/tabs). For settings categories that lead to a section and offer Back to return, follow the [preferences dialog pattern](./preferences-dialog).
- When users switch the same underlying records between List and Cards, use [`ToggleButtonGroup`](/salt/components/toggle-button/usage#view-switching). This changes presentation rather than the navigation destination.
- When you need to present task actions rather than wayfinding, use a Button bar or toolbar instead.

## How to build

Use [`NavigationItem`](/salt/components/navigation-item) for a simple horizontal group of destination links. Group the items in a labelled navigation region. For grouped destinations, see [Mega menus](#mega-menus).

For new vertical navigation, use [`VerticalNavigation`](/salt/components/vertical-navigation), which provides the navigation region and item list. Give the region an accessible name. Existing vertical `NavigationItem` implementations can remain during migration, but prefer `VerticalNavigation` for new work.

### Links and cards

- Use [`Link`](/salt/components/link) for a text link to another page, a resource such as a document, or a section on the same page.
- Use [`LinkButton`](/salt/components/link-button) when a destination needs button-like prominence, such as a primary call to action in a banner or empty state. Use [`Button`](/salt/components/button) for on-page actions such as submitting a form or opening a dialog.
- Use [`LinkCard`](/salt/components/card/examples#link-card) when the whole card leads to one destination. Keep its contents static; don't nest buttons or other links inside it.
- Use a static [`Card`](/salt/components/card/usage#interactable-elements) when its content contains separate links or buttons. Each control then has its own destination or action.
- Use [`InteractableCard`](/salt/components/card/examples#interactable-card) for an action, or within `InteractableCardGroup` for selection. Follow the [selectable-card pattern](/salt/patterns/selectable-card) for that selection. For whole-card navigation, use `LinkCard`.

### Mega menus

Use [`MegaMenu`](/salt/components/mega-menu) to organize many related destinations into groups in the main navigation. It suits complex site structures where users benefit from seeing groups of links together.

If any top-level item needs a mega menu, use the same mega menu pattern for all top-level items in that navigation system. For simple structures or small screens, consider a simpler navigation pattern; mega menus can be difficult to use on mobile. See the [mega menu guidance](/salt/components/mega-menu/usage#when-not-to-use) for alternatives and composition details.

### Supporting navigation

- Use [`Breadcrumbs`](/salt/components/breadcrumbs) to show the current location within a hierarchy and provide a path back to earlier levels. Breadcrumbs complement the main navigation.
- Use [`SkipLink`](/salt/components/skip-link) to let keyboard and screen reader users bypass repeated headers or navigation and reach the main content.
- Use [`Pagination`](/salt/components/pagination) to move between pages of search results or data. For a sequential workflow, use [`Stepper`](/salt/components/stepper) to communicate progress and the [button bar pattern](/salt/patterns/button-bar) to move between steps.

### Anatomy

Main navigation has horizontal and vertical layouts. You can use them on their own or combined together depending on your navigation structure:

1. **Horizontal navigation**: Uses a horizontal group of `NavigationItem` links for simple destinations, or `MegaMenu` triggers for grouped destinations.
2. **Vertical navigation**: Uses the `VerticalNavigation` component family to arrange destinations and expandable groups in a vertical layout. An expansion trigger reveals nested items. If the parent has a single trigger, place any overview destination as the first nested item.

## Horizontal navigation

You would normally use a horizontal navigation within an application header, at the top of a page. Use it when you need a navigation that:

- Is always displayed in a prominent and consistent location.
- Affords movement from one set of content to another regardless of where the user is in the website or app.

## Vertical navigation

A common navigation practice is to have the primary categories that represent the main sections of your website or application in a vertical layout, usually placed on the left side of the screen. These primary categories can expand to reveal secondary categories or subcategories when selected, creating a hierarchical structure. It can display many navigation items at once. Use it when:

- You need to show many top-level views.
- You have deep navigation structures.

Read more in the [vertical navigation pattern](/salt/patterns/vertical-navigation).

### Fixed navigation pane

Typically, the vertical navigation remains fixed in width when the user resizes the browser. You can set it to the width of your choice. However, you should consider the overall label length, theme, density and screen size you are designing for.

When your application is responsive, the content area should use its own layout grid. As the user adjusts their browser width, the navigation remains fixed until reaching a specified breakpoint, with only the content area adapting responsively based on the viewport.

### Responsive navigation pane

You can configure a vertical navigation for fully responsive application experiences. This is useful when you need to reserve more space for the content area, such as for a chart that you want to display in full at as many viewport sizes as possible.

Use the underlying layout grid to set a minimum width for your navigation pane and adjust your content area based on your predefined breakpoints.

## Combined navigation

Combine both horizontal and vertical navigation when users need to:

- Navigate between multiple apps with horizontal navigation, and multiple pages within each app with vertical navigation.
- Navigate other complex hierarchies.

<Diagram
  src="/img/patterns/navigation/combined-nav-behaviour.png"
  alt="Example showing a combined navigation pane."
  caption="Example showing a combined navigation pane."
  border
/>

Combined navigation can be useful in website or application contexts when you want to provide users with a versatile and efficient way to navigate complex content or features. It's ideal when your experience comprises multiple sub-apps, pages or sections, which in turn also require their own navigation.
