## When to use

Use this pattern in a container component when the state belongs to the content area itself:

- When a bounded region or local content area needs a loading, empty, warning, error, or success state.
- When content is loading and no useful previous content is available.
- When a container has no data to show and you need an empty-state message.
- To share information, warnings, or errors with users that relate to the current content area.
- When the user has successfully submitted content or completed an action.

## When not to use

- For essential platform-wide maintenance or outage notices, use [SystemStatus](/salt/components/system-status/usage).
- For an individual service's current condition, show [StatusIndicator with descriptive text](/salt/components/status-indicator/usage) alongside that service. A service being degraded is different from the interface failing to load or refresh its data.
- When a refresh fails and previously loaded content remains visible, use [Banner](/salt/components/banner/usage) in the related container. Use a page-level Banner when the issue affects the whole page.
- For a nonblocking notification that does not need to remain in the content area, consider [Toast](/salt/components/toast/usage). Essential error details and recovery actions must remain available in the owning view.
- For field validation or a failed save, follow the [Forms feedback guidance](/salt/patterns/forms#choosing-feedback). Use [Dialog](/salt/components/dialog/usage) only when the user must make a decision that requires interrupting the workflow.
- When the state is not tied to a container, use inline text or another component instead.

## How to build

### Choosing how to communicate loading and recovery

Choose feedback according to whether useful content is already available and
which part of the task is affected:

- **No content yet:** use Content status within the affected region for initial loading, an initial-load failure with Retry, or an empty result after a successful request. A failed request is not an empty result.
- **Refreshing existing content:** retain the content and show a local loading indication, such as a [loading Refresh button](/salt/components/button/examples#loading).
- **Refresh failed, previous content remains:** show a [Banner](/salt/components/banner/usage) in the related container, explain that the data was not updated, and offer Retry. For example: “Couldn't refresh. Showing previously loaded data.”
- **The whole page is affected:** use a page-level Banner.
- **An essential platform-wide condition:** use [SystemStatus](/salt/components/system-status/usage) for a maintenance notice or outage affecting the application. A failed request in one region does not by itself establish a platform-wide outage.

Choose severity according to whether users can safely continue or their task is
blocked, rather than treating every failed request as the same severity.

Preserve filters, selection, scroll position, and keyboard focus during a refresh
where they remain valid. Updating the displayed records must not overwrite an
unsaved editing draft. If a new search, filter, or account changes the scope, make
clear that any retained rows are previous results; do not present them as matching
the new request.

When freshness matters, show when the data was last updated. Retaining content
does not make stale data safe: disable or revalidate actions that require current
data until its freshness is established.

### Empty and no matching results

Choose the message according to why no records are displayed:

- **No records in the current scope:** after a successful request, explain that no records are available in this scope. Offer an onward action only when it applies to the task.
- **No matching results:** explain that no items match the current search or filters. Keep these criteria visible so users can adjust or clear them; do not clear them automatically. A filtered result with no rows does not establish that the whole dataset is empty. Follow the [List filtering guidance](/salt/patterns/list-filtering#no-matches).
- **Request failed:** describe the failure and offer Retry using the [loading and recovery guidance](#choosing-how-to-communicate-loading-and-recovery). Successful no-match results are not errors and do not need Retry.

### Anatomy

The content status consists of three functional areas:

1. **Visual indicator:** Content status can use [`StatusIndicator`](/salt/components/status-indicator), [`Progress`](/salt/components/progress) or [`Spinner`](/salt/components/spinner) for its visual indicator.
2. **Text:** Text elements serve as supporting messages.
3. **Button:** Buttons are optional and can be added to reload content or perform a custom action.

### Layout

- Use [`StackLayout`](/salt/components/layouts/stack-layout) to arrange the visual indicator, title, supporting message, and optional action vertically.
- Use [`Text`](/salt/components/text) for the title and supporting message.
- Add a [`Button`](/salt/components/button) only when the status offers an action, such as reloading content.

### Supporting messages

- **Have a clear hierarchy**: Your titles should be stand-alone, revealing key information your users need to know without relying on the supporting message, which users may skim over, e.g., “Login required.”
- **Be helpful**: If it’s possible for your users to resolve or rectify an issue, make sure you state this clearly, e.g., “You can log in to access this data.”
- **Keep it simple**: Try to limit titles to a single line and supporting messages to no more than three lines.

## Warning message

Use the warning status to inform users of an issue or potential issue related to their current task. Use this for issues that don't prevent the user from continuing or completing their task. For example, warn about a limitation affecting the content in this region. For essential platform-wide notices, use [SystemStatus](/salt/components/system-status/usage).

Use the error status to communicate a critical issue that prevents the user from continuing or completing the task. This could include missing content or user information required.

2. Identify and explain the issue.
3. Provide a resolution.

## Label only

Use the label only content status when you:

- Have limited space.
- Don’t want to display spinners due to performance concerns, e.g., on low performance devices.
- Want to avoid busy visual UI and animations.

For example, use for displaying a loading status in a data grid or in a combo box list.
