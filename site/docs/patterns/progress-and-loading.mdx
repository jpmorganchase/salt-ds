<Callout title="Note">

This page describes the north star for progress and loading in Salt. Some of the components and behaviors it describes aren't available yet.

</Callout>

## Principles

Users should always know:

- **Where they are**, when they're moving through a multi-step task.
- **How much is left**, when the system can measure its work.
- **That the system is working**, when it can't.
- **What's coming**, when content is on its way.

Every indicator in the family shares the same visual and spoken language, so users learn it once. For actions that usually finish quickly, an optional delay avoids flashing an indicator.

## When to use

Use this pattern whenever users have to wait, or need to know where they are in a process.

## Comparison

The family answers different questions. The first difference is who is doing the work. A stepper tracks the user's work. Everything else tracks the system's work.

| Indicator              | Shows                                           | Answers the question            | Example                                     |
| ---------------------- | ----------------------------------------------- | ------------------------------- | ------------------------------------------- |
| Stepper                | The user's place in a multi-step task           | "Where am I, and what's next?"  | Personal details → Payment → Review         |
| Determinate progress   | How much of a system task is complete           | "How much is left?"             | Uploading a file, exporting a report        |
| Indeterminate progress | That the system is working, for an unknown time | "Is it still working?"          | Submitting a form, refreshing a table       |
| Skeleton               | The layout of content that's on its way         | "What's coming?"                | Loading a list, a table or a set of cards   |
| Page loader            | That the application is opening                 | "Is the application opening?"   | Opening the application for the first time  |

If you're showing an amount rather than a task, such as storage used, use a meter instead of progress. See [progress or meter](#progress-or-meter).

## Quick test

Ask these questions in order.

1. **Who is doing the work?** If the user moves forward by completing steps, use a stepper. If the system is working, go to question 2.
2. **Can you measure how much is done?** If yes, use determinate progress. If not, go to question 3.
3. **Is the application opening, with nothing else to show yet?** If yes, use a page loader. If not, go to question 4.
4. **Do you know the layout of the content that's loading?** If yes, use a skeleton. If not, or users are waiting for the result of an action, use indeterminate progress.

Then choose the shape of a progress indicator by the space it's in. See [shape](#shape).

## Progress

Progress shows system work. It's a single component with two choices: its motion and its shape. Give it a value and it fills. Leave the value out and it loops.

### Motion

Motion tells users whether the work can be measured.

- **Determinate progress fills.** It moves toward a clear end, and only moves forward.
- **Indeterminate progress loops.** It moves continuously, with no end, until the work finishes.

A fill must never loop, and a loop must never look like a fill. A bar that fills from empty to full and then starts again tells users that the work has restarted.

When you don't know the size of a task yet, start with indeterminate progress and switch it to determinate in the same place once you do. The indicator keeps its shape and position, so nothing moves. For example, a circular indicator in a download button loops while the download starts, then fills as it runs.

### Shape

Shape depends on the space, not on the meaning. Both shapes can fill or loop, and share the same visual language, so users read them in the same way.

| Shape    | Use it                                                                                                   |
| -------- | -------------------------------------------------------------------------------------------------------- |
| Circular | In compact spaces, inside controls such as buttons, and when centered in a region that's loading         |
| Linear   | In wide or thin spaces, and alongside content that stays visible, such as a file row, a card or a table   |

Indeterminate circular progress is what's often called a spinner. There's no separate spinner component.

### Text

Pair progress with text, so users know what's happening without having to interpret the indicator.

- **Label:** what's happening, such as "Uploading report.pdf".
- **Value:** how much is done, in units that make sense to users, such as "3 of 5 files" or "45 of 100 MB". Use a percentage only when there's no better unit.
- **Helper text (optional):** extra context, such as "About 2 minutes left".

### States

Progress can end in more than one way. Show the outcome in place, using an icon and text as well as color. Keep it on screen until users move on or dismiss it.

- **Active (`status="active"`, the default):** the work is running.
- **Paused (`status="paused"`):** the work has stopped and can be resumed.
- **Success (`status="success"`):** the work finished successfully. For simple actions, the result is the confirmation. For example, a new item appearing in a list needs no extra success message.
- **Error (`status="error"`):** the work failed. Explain why, and offer a way to retry.

Reaching `max` fills the indicator but leaves the task active. For example, all bytes may have uploaded while the server is still processing the file. Set `status="success"` only when the application confirms that the task has finished.

Offer actions alongside progress when they help, such as pause, resume, cancel and retry. These actions belong to the task owner: changing the indicator's status doesn't pause or cancel the underlying operation. Remove the indicator when cancelling a task; removal doesn't signal success.

### Progress or meter?

Both show a value within a range, but they describe different things.

|                      | Progress                                   | Meter                                              |
| -------------------- | ------------------------------------------ | -------------------------------------------------- |
| Shows                | How much of a task is complete             | An amount within a known range                     |
| Changes              | Moves forward until the task ends          | Goes up or down, and has no end                    |
| Example              | Uploading a file                           | Storage used, or a credit limit used               |

If the value would still make sense when nothing is happening, use a meter.

## Stepper

A stepper shows the user's place in a multi-step task, such as a [wizard](/salt/patterns/wizard). Use it for processes with three or more steps, and keep step labels short.

Classify an indicator by what it tracks, not by how it looks. An indicator is a stepper if:

- Its unit is named, separate steps, rather than a continuous value.
- The user moves it forward, rather than the system.
- It moves one whole step at a time.

In narrow layouts, use a compact stepper. It shows the steps as a single track, with the current step as text, such as "Step 2 of 4: Payment details".

## Skeleton

A skeleton holds the place of content that's loading, and shows its layout. This makes the wait feel shorter, and nothing moves when the content arrives.

|                | Skeleton                                                        | Indeterminate progress                                           |
| -------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| Use it for     | Loading content with a known layout, such as a list or a table  | Loading content with an unknown layout, or waiting for an action |
| What it shows  | The shape of the content                                        | That the system is working                                       |
| Space it takes | The size of the content it replaces                             | Only the space it needs                                          |

Build skeletons from the same text sizes and spacing as the content they replace, so they match its layout at every density.

## Page loader

A page loader is a full-page loading state that you compose from other components. Use it only when the application first opens and there's nothing else to show. It contains:

1. **Logo or application name (optional):** supplied by your application, so users know which application is opening.
2. **Progress indicator:** chosen in the same way as anywhere else. Use determinate progress if you can measure how much of the application has loaded, such as 3 of 5 modules.
3. **Status message:** a short, visible message, such as "Loading your accounts".

Stack these with a [`StackLayout`](/salt/components/layouts/stack-layout), and center it in the viewport. As soon as the application's frame, such as its header and navigation, can show, replace the page loader with skeletons or progress in the regions that are still loading.

## Loading inside components

Components that load content or start actions show loading in the same way, so users recognize it everywhere.

- **Buttons:** a [button](/salt/components/button) that starts an action shows circular progress, keeps its size and accessible name, and can't be pressed again until the action completes. Reserve the icon's space even during an optional display delay. The button owns the task's announcements and sets `disableAnnouncer` on its nested progress indicator. This prevents duplicate submissions and announcements.
- **Lists and combo boxes:** a [list box](/salt/components/list-box) or [combo box](/salt/components/combo-box) shows a loading state in place of its options, then the options as they arrive.
- **Tables and data grids:** show a skeleton on first load. When refreshing data that's already visible, keep it on screen and show linear progress above it.
- **Containers:** follow the [content status](/salt/patterns/content-status) pattern.

## Long-running tasks

Don't make users wait for tasks that take a long time. Let them keep working, and keep the task's progress and outcome where users can find them again.

- **Progress:** show it in place, where the task started, such as in the file row or the card. For tasks that continue across pages, also show it in a list of tasks users can return to.
- **Outcome:** when the task completes or fails, show a [banner](/salt/components/banner) where the task started, and let users open the result or retry. The banner stays until users dismiss it.
- **Very long tasks:** also notify users through other channels, such as the application's notifications or email, so they find out even if they've left.

Don't use a [toast](/salt/components/toast) as the only place for a task's progress or outcome. Toasts appear away from the content they relate to, are easy to miss with screen magnification or on large displays, and are hard to return to. If users have moved to a different part of the application, a toast can tell them that a task has finished, as long as it stays until they dismiss it, and the outcome is also available in place.

## Timing

Match loading to how long users will wait. See [duration](/salt/foundations/duration) for more detail.

Progress appears immediately by default (`delay={0}`). Set `delay={1000}` when quick tasks should finish without showing an indicator.

- **With a 1 second delay:** tasks that succeed before the indicator appears stay hidden and aren't announced by Progress. Errors show immediately, even during the delay.
- **Once shown:** keep an indicator on screen for a short minimum time, so it doesn't flicker on and off.
- **1–10 seconds:** show the indicator chosen with the [quick test](#quick-test).
- **Over 10 seconds:** change the status message to say the system is still working, such as "Still working, please wait". If the work can't complete, show an error and offer a way to retry or cancel.

<GuidanceCallout type="positive" customPillText="Best practices">
- Use determinate progress whenever you can measure the work. Progress that moves forward feels faster than a loop.
- Describe what's happening in text, such as "Uploading report.pdf", rather than relying on the indicator alone.
- Show values in units that users understand, such as files or megabytes.
- Match a skeleton to the real layout of the content.
- Keep content on screen while it refreshes, and show progress alongside it.
</GuidanceCallout>

<GuidanceCallout type="negative">
- Don't show a value you can't measure, or fill an indicator that's really looping.
- Don't use progress to show steps in a user's journey, or a stepper to show system work.
- Don't use a page loader for actions or for moving between pages.
- Don't show more than one indicator for the same content, such as progress on top of a skeleton.
- Don't block the whole page for work that only affects one region.
- Don't rely on a toast for a task's progress or outcome, or dismiss outcomes automatically.
- Don't confirm simple actions whose result is already visible.
</GuidanceCallout>

## Accessibility

Every indicator in the family sounds the same to screen reader users as it looks to sighted users.

- **Stepper:** screen readers announce the current step and its position, such as "Step 2 of 4: Payment details". Steps aren't announced as progress.
- **Determinate progress:** screen readers read the label and the value from the progress bar, in the same units as the visible text, so changes of value aren't announced separately. `status="success"` and `status="error"` announce the outcome. Reaching `max` alone doesn't announce completion.
- **Indeterminate progress:** in either shape, screen readers announce the label when the indicator appears and repeat it while loading continues. Removing the indicator isn't announced, as it could mean the task was cancelled. When a task completes or fails, that's announced, and a region that's loading announces when its content has loaded. Announcements are polite and never interrupt users.
- **Meter:** screen readers announce a meter's value as an amount, not as progress through a task.
- **Skeleton:** skeletons are hidden from screen readers. The region that's loading is marked as busy, and screen readers announce when its content has loaded.
- **Page loader:** screen readers announce the status message in the same way as indeterminate progress.
- **Progress states:** success and error outcomes are announced and shown with an icon. Paused progress displays "Paused" and includes the state in its accessible value text.
- **Reduced motion:** when users have turned on reduced motion, loops slow down or stop, skeletons stop shimmering, and text carries the message.

Choose one owner for live announcements. When a button or loading region already announces the task, set `disableAnnouncer` on its nested Progress. This suppresses loading, success and error announcements while preserving the progress bar's accessible name, role and value. Re-enabling announcements doesn't replay a success or error that occurred while they were disabled. Use `completionAnnouncement={null}` when only the success announcement should be suppressed.

## Suggested API

The Progress API below is available in `@salt-ds/lab`. The other APIs describe the north star, for discussion, and build on the `loading` and `loadingAnnouncement` props that `Button` has today.

The API works with React 19's Suspense, transitions and actions. It also works with earlier versions of React, where you control loading with the `loading` props instead.

| React 19 feature                       | Use it with                                                                          |
| -------------------------------------- | ------------------------------------------------------------------------------------ |
| Suspense                               | `LoadingRegion`, with a skeleton or progress as its fallback                          |
| `useTransition`, `useDeferredValue`    | Progress alongside content that stays on screen, using `isPending`                   |
| Form actions, `useFormStatus`          | A submit button's `loading` prop                                                     |
| `useActionState`                       | A button's `loading` prop, and a banner for the outcome                              |
| `useOptimistic`                        | No indicator. The result appears straight away.                                      |
| Streaming server rendering             | Skeletons and progress, which animate with CSS before the page is interactive        |

### Progress

One component covers both shapes. Give it a value and it fills. Leave the value out and it loops.

```tsx
import { Progress } from "@salt-ds/lab";

// Determinate: fills toward the end.
<Progress
  shape="linear"
  value={3}
  max={5}
  label="Uploading files"
  getValueText={(value, max) => `${value} of ${max} files`}
/>;

// Indeterminate: loops until the work finishes.
<Progress shape="circular" label="Loading accounts" />;

// Starts indeterminate, then fills in place once the size is known.
<Progress
  shape="circular"
  value={totalBytes ? downloadedBytes : undefined}
  max={totalBytes}
  label="Downloading report.pdf"
/>;

// A full value can still be active while the server finishes processing.
<Progress
  value={100}
  label="Processing report.pdf"
  description="Upload complete. The server is still processing the file."
/>;

// The task owner confirms success separately from its measured progress.
<Progress value={100} label="Report ready" status="success" />;
```

| Prop                     | Type                                           | Default                 | Description                                                                                                  |
| ------------------------ | ---------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------ |
| `shape`                  | `"linear" \| "circular"`                       | `"linear"`              | The shape. Choose it by the space it's in.                                                                     |
| `value`                  | `number`                                       | –                       | How much is done. Leave it out for indeterminate progress. Reaching `max` doesn't change the task's status.      |
| `min`, `max`             | `number`                                       | `0`, `100`              | The range of the value.                                                                                        |
| `label`                  | `ReactNode`                                    | –                       | What's happening. Shown, and used as the accessible name.                                                       |
| `description`            | `ReactNode`                                    | –                       | Helper text, such as "About 2 minutes left".                                                                    |
| `getValueText`           | `(value, max, min) => string`                   | Percentage, such as 38% | The value that's shown and exposed to screen readers, such as "3 of 5 files".                                  |
| `status`                 | `"active" \| "paused" \| "success" \| "error"` | `"active"`             | The state of the task. Set `"success"` when the task has finished successfully.                                 |
| `size`                   | `"small" \| "medium" \| "large"`              | `"medium"`              | Circular only. The size of the indicator.                                                                       |
| `delay`                  | `number`                                       | `0`                     | Milliseconds to wait before showing. Set `1000` to hide quick tasks; errors and initially successful tasks show immediately. |
| `disableAnnouncer`       | `boolean`                                      | `false`                 | Suppresses all live announcements when the task owner handles them. The accessible name and value remain available. |
| `completionAnnouncement` | `string \| null`                               | `"finished {label}"`    | Success announcement for `status="success"`. Set `null` to suppress only this announcement.                    |

### Meter

A meter shares the value props with progress, but has no indeterminate state, timing or announcements, because it isn't a task.

```tsx
import { Meter } from "@salt-ds/core";

<Meter
  value={72}
  max={100}
  label="Storage used"
  getValueText={(value, max) => `${value} of ${max} GB`}
/>;
```

### Stepper

A compact stepper is a variant of `Stepper`, and uses the same `Step` children. To switch between them in different layouts, you only change the variant.

```tsx
import { Step, Stepper } from "@salt-ds/core";

<Stepper variant={isNarrow ? "compact" : "default"} aria-label="Checkout">
  <Step label="Personal details" stage="completed" />
  <Step label="Payment details" stage="active" />
  <Step label="Review" />
</Stepper>;
```

### Skeleton and loading regions

`LoadingRegion` marks a region as busy, shows a fallback while it loads, and announces when the content has loaded. The fallback can be a skeleton or progress.

Without a `loading` prop, `LoadingRegion` is a Suspense boundary. It shows the fallback while its children suspend, such as when they read data with `use`.

```tsx
import { LoadingRegion, Skeleton, StackLayout } from "@salt-ds/core";

function AccountListSkeleton() {
  return (
    <StackLayout gap={1}>
      <Skeleton variant="text" styleAs="h2" width="40%" />
      <Skeleton variant="text" lines={3} />
      <Skeleton variant="rectangle" height={120} />
    </StackLayout>
  );
}

<LoadingRegion
  loadingAnnouncement="Loading accounts"
  completionAnnouncement="Accounts loaded"
  fallback={<AccountListSkeleton />}
  errorFallback={({ retry }) => (
    <Banner status="error">
      <BannerContent role="status">Accounts couldn't be loaded.</BannerContent>
      <BannerActions>
        <Button onClick={retry}>Retry</Button>
      </BannerActions>
    </Banner>
  )}
>
  <AccountList accountsPromise={accountsPromise} />
</LoadingRegion>;
```

With a `loading` prop, you control it yourself. This works with any version of React.

```tsx
<LoadingRegion
  loading={isLoading}
  loadingAnnouncement="Loading accounts"
  completionAnnouncement="Accounts loaded"
  fallback={<AccountListSkeleton />}
>
  <AccountList accounts={accounts} />
</LoadingRegion>;
```

| Prop                     | Type                                  | Description                                                                          |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------------------------------ |
| `loading`                | `boolean`                             | Whether the region is loading. Leave it out to use the region as a Suspense boundary. |
| `fallback`               | `ReactNode`                           | What to show while the region loads, such as a skeleton or progress.                 |
| `errorFallback`          | `({ error, retry }) => ReactNode`     | What to show if loading fails. `retry` tries to load the region again.               |
| `loadingAnnouncement`    | `string`                              | What screen readers announce while the region loads.                                 |
| `completionAnnouncement` | `string \| null`                      | What screen readers announce when the content has loaded.                            |
| `minDuration`            | `number`                              | Once the fallback shows, the minimum milliseconds it stays, so it doesn't flicker. Doesn't apply to Suspense, as React decides when fallbacks are removed. |

`Skeleton` has no state or effects, so it can render as a server component and stream as a Suspense fallback. Its shimmer is CSS only, so it animates before the page is interactive.

Text skeletons take the same `styleAs` values as `Text`, so they match the size of the text they replace at every density. Skeletons are hidden from screen readers, and stop shimmering when users have turned on reduced motion.

### Refreshing content

When content refreshes, keep it on screen and show progress alongside it. With a transition, React keeps the current content until the new content is ready. Set `delay={1000}` when quick refreshes should show no indicator.

```tsx
const [isPending, startTransition] = useTransition();

<Button onClick={() => startTransition(refreshAccounts)}>Refresh</Button>;

{isPending && <Progress shape="linear" label="Refreshing accounts" delay={1000} />}
<AccountTable accounts={accounts} />;
```

### Loading inside components

Components that load content or start actions take the same `loading` and `loadingAnnouncement` props as `Button`.

```tsx
<Button loading={isSaving} loadingAnnouncement="Saving">
  Save
</Button>;

<ComboBox loading={isFetching} loadingAnnouncement="Loading options">
  {options}
</ComboBox>;
```

### Actions

With form actions, a submit button follows the form's pending state. Show the outcome of the action in a banner.

```tsx
function SubmitButton({ children }: { children: ReactNode }) {
  const { pending } = useFormStatus();
  return (
    <Button type="submit" loading={pending} loadingAnnouncement="Saving">
      {children}
    </Button>
  );
}

function DetailsForm() {
  const [state, formAction] = useActionState(saveDetails, null);

  return (
    <form action={formAction}>
      {state?.error && (
        <Banner status="error">
          <BannerContent role="status">{state.error}</BannerContent>
        </Banner>
      )}
      {/* Form fields */}
      <SubmitButton>Save</SubmitButton>
    </form>
  );
}
```

For simple actions, use `useOptimistic` to show the result straight away, with no indicator. If the action fails, React removes the result. Show a banner that explains why.

### Page loader

A page loader is a composition, not a component. The progress label is the visible status message, so screen readers announce it too. Use it as the fallback of the Suspense boundary at the root of your application.

```tsx
function AppLoader() {
  return (
    <StackLayout
      align="center"
      gap={3}
      style={{ minHeight: "100vh", justifyContent: "center" }}
    >
      <AppLogo />
      <Progress shape="circular" size="large" label="Loading your accounts" />
    </StackLayout>
  );
}

<Suspense fallback={<AppLoader />}>
  <App />
</Suspense>;
```

When moving between pages, use a transition, so the current page stays on screen until the next one is ready.

### Long-running tasks

Show progress in place, then a banner with the outcome where the task started.

```tsx
{status === "uploading" ? (
  <Progress
    value={uploaded}
    max={total}
    label="Uploading files"
    getValueText={(value, max) => `${value} of ${max} files`}
  />
) : (
  <Banner status={status === "failed" ? "error" : "success"}>
    <BannerContent role="status">
      {status === "failed"
        ? "2 of 5 files couldn't be uploaded."
        : "5 files uploaded."}
    </BannerContent>
    <BannerActions>
      {status === "failed" && <Button onClick={retry}>Retry</Button>}
      <Button aria-label="Dismiss" appearance="transparent" onClick={dismiss}>
        <CloseIcon aria-hidden />
      </Button>
    </BannerActions>
  </Banner>
)}
```
