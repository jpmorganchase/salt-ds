Create an icon by defining its meaning, developing it beside its closest family and reviewing it at interface size. The [icon design guidelines](/salt/foundations/assets/icon-design) are the visual standard. This page describes the design and contribution workflow; the [repository maintenance guide](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md) provides detailed construction, export and validation instructions.

## Define the meaning

Search the [catalogue](/salt/foundations/assets/index#all-icons) before creating artwork. Record the intended object, action or state, where it will appear and the icons it needs to work beside. Decide whether a new icon is needed or an existing symbol with a clear label will serve the purpose.

Choose a name that describes the intended meaning and follows its family. For example, **Remove bookmark** describes removing an item from bookmarks more clearly than “Unsave.” Distinguish a generic object, a file type and an official brand mark before drawing them; these require different source material and treatments.

For changes to an existing icon, preserve its public name and meaning unless a rename is part of the agreed contribution. Keep the previous artwork for comparison, and identify the specific problem the change should improve.

## Construct the artwork

Start from the nearest approved family. Reuse its base silhouette, proportions, landmarks and repeated marks. Build editable vector geometry on Salt's 16 × 16 output canvas, and compare it at 12px throughout the process. A larger reference or generated concept can help explore a direction, but is not a production system icon.

Apply the design standard to the final paint: softened inner joins and opening corners, sharp outward-facing corners and flat ends, with natural curves preserved. Use shared constructions for recurring frames and marks so new family members inherit the same treatment. There is no need to change the design rules or add a special validator for every new icon.

Keep identifying marks at an appropriate family weight. Improve spacing, placement and detail before thinning them to make them fit. See [Stroke weight](/salt/foundations/assets/icon-design#stroke-weight) and [Calibrate the amount of welding](/salt/foundations/assets/icon-design#calibrate-the-amount-of-welding).

### Record modifier decisions

For an action or state, record the base object, modifier meaning and intended placement. Follow [Action and state modifiers](/salt/foundations/assets/icon-design#action-and-state-modifiers): replace secondary contents before crowding an internal mark, and reserve transparent clearance for actual overlaps or visual collisions.

Review the modifier's own joins separately from its relationship with the base. A plus can have welded inner corners while remaining separate from a calendar. Explain any departure from its nearest siblings.

### Develop outline and solid together

Choose which surface can fill without losing the object's meaning. Keep common contours, line weights, feature positions and action marks consistent. Compare the final pair in the same position as well as side by side. Either variant can lead: a strong solid silhouette can provide the boundary from which to draw an inset outline.

Use the [text-line guidance](/salt/foundations/assets/icon-design#text-lines-and-inverse-openings) for simulated content. Painted bars can retain sharp ends while inverse slots have softened interior corners; line rhythm and apparent weight must still match.

The existing Import and Export solid exports are compatibility aliases for their open-line symbols. They do not establish a pattern for new solid variants: add a solid companion only when it offers a coherent filled treatment.

### Share symbols on the final canvas

Reuse common symbol geometry rather than redrawing each occurrence. Within a status pair, positive and inverse marks keep the same contour and placement. Compare the emphasis of different status symbols together, especially at 12px, while allowing container-specific optical adjustments.

Contributors should use the repository's shared mark composition so fitting a container does not inadvertently resize or move its symbol. The [maintenance guide](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md#share-symbols-on-the-final-canvas) covers this mechanism and its existing family owners.

## Fit every export to the viewBox

Check the complete painted shape, not just the path centerlines. Preserve aspect ratio, keep paint inside the 16-unit frame and compare apparent size against neighboring icons. The ordinary fit targets a **15.5-unit longest painted dimension at width 1.5**; optical exceptions and shared family frames preserve balance and common landmarks.

Check important straight edges on the final 12px pixel grid, then compare 16px and actual component placement. Retain an optical frame that preserves useful alignment instead of enlarging every drawing to the maximum span. See [pixel alignment](/salt/foundations/assets/icon-design#align-important-edges-to-the-pixel-grid).

Judge the exported pair after fitting. Two identical source features can end up at different positions if their full drawings fit differently. Record a justified optical adjustment in the shared fit configuration rather than adding arbitrary padding or stretching an icon. Official brand marks and the existing full-canvas checkmark surfaces retain their designated frames.

The [export-fitting instructions](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md#fit-every-export-to-the-viewbox) explain construction units, shared frames, optical targets and the generated fit manifest.

## Construct transparent cutouts

Follow the [cutout guidance](/salt/foundations/assets/icon-design#transparency-and-cutouts). Derive clearance from the actual foreground paint, including its cap corners, tips and curved joins. Recheck it whenever that foreground changes.

Compare gaps at the two themed weights and at native size. An opening that reaches the outer edge must remain fully open, without a border crossing its mouth. Check light and dark backgrounds; painted background-colored patches are not transparent cutouts.

For implementation, use the maintenance guide's [painted-gap calculations and contour construction](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md#construct-transparent-cutouts).

## Preserve official brand artwork

Start from the owner's official vector source and usage guidance. Preserve its contours and proportions, record provenance and retain required license information. Follow the [brand-logo rule](/salt/foundations/assets/icon-design#brand-logos); do not restyle a logo with Salt corner treatments. Existing source files and export choices are recorded in the [brand source notes](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/scripts/artwork/brands/README.md).

## Review the design

### Use the existing review surfaces

Compare the complete affected family in the site's [Icons catalogue](/salt/foundations/assets/index#all-icons), the existing Storybook **Icons/Icon** stories and the relevant component examples. **Icon QA** provides size and CSS-mask examples. Follow the [repository setup and review instructions](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md#use-the-existing-review-surfaces) to run them.

Review both variants at actual **12px and 16px**, on **light and dark backgrounds**, plus an enlarged view. Use 12px at **device pixel ratio 1 and 100% browser zoom** as the primary clarity check, then confirm higher-density screens. Display pixel density is separate from the Salt density setting. Start with the themed widths: **4/3 for high/medium density** and **1 for low/touch/mobile**. Also inspect the **0.67** SVG reference and the **1.5** fitting width. Confirm actual rendered dimensions: the component's `size` prop is a density-based multiplier, not a pixel value.

For a whole-scale review, cover multipliers 1–4 at every density using the [published size table](/salt/foundations/assets/index#scaling-icons). Review generated components and CSS masks separately, since masks keep baked stroke widths.

Hide names for the first recognition pass, then inspect the intended interface context. Compare before and after for the whole affected family. Retain a change only when it improves the identified problem without weakening recognition, weight or common landmarks. Distinguish an expert visual judgment from feedback gathered from users.

### Check corners and exceptions

Inspect the complete unmarked drawing as well as any annotated review map. Use the [geometry rule](/salt/foundations/assets/icon-design#geometry) to classify exposed inner joins, isolated opening corners, already smooth transitions, outward corners and hidden contacts. An unenclosed cross still has inner joins. Then [calibrate the amount of softening](/salt/foundations/assets/icon-design#calibrate-the-amount-of-welding) against local band width, straight length, clearance and native-size recognition. Review equivalent repeated features consistently. A detector result can suggest where to inspect; it does not decide whether a weld is too strong, and an empty result does not establish approval.

For any retained sharp interior corner, save a 12px and 16px comparison showing why softening would obscure a feature or close a necessary opening. Record the feature and reason beside the artwork. Unresolved decisions stay unresolved. The [maintenance guide](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md#reuse-the-interior-contour-profile) explains review records, evidence and checks that detect stale approvals.

## Add and integrate a new icon

Implement durable artwork changes in the owning recipe, rather than editing generated SVGs. Keep the following together in a contribution:

- The source construction and registration for each requested variant.
- A clear name, useful search synonyms and an appropriate catalogue category.
- Generated SVGs, React components, CSS masks, icon lists and fit metadata.
- Native-size and enlarged family comparisons, with exceptions and coverage recorded.
- Relevant validation results and a changeset for consumer-visible artwork or exports.

### Website synonyms and categories

Choose terms people will use to find the icon without blurring its meaning. One base metadata entry covers outline and solid. Use lowercase terms, and include individual words or a compact equivalent for important phrases because catalogue search normalizes query spaces.

Verify representative queries and both variant filters in the website catalogue. Storybook searches component names and does not test website synonyms. Preserve intentional legacy aliases and deprecation metadata. See [registration and metadata instructions](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md#add-and-integrate-a-new-icon) for exact files and schemas.

## Commands and acceptance

From the repository root, generate the complete package and check the affected names:

```sh
yarn workspace @salt-ds/icons generate:icons
yarn workspace @salt-ds/icons validate:icons
yarn node packages/icons/skills/salt-icons/scripts/check-integration.mjs --repo . new-name
```

Generation and artwork validation use the repository's Playwright dependency and installed Chrome. The [maintenance guide](https://github.com/jpmorganchase/salt-ds/blob/main/packages/icons/MAINTAINING.md#commands-and-acceptance) covers component tests, corner-review records and additional checks for the change being made.

Before handoff, complete the [design review checklist](/salt/foundations/assets/icon-design#design-review), inspect the generated changes and verify discovery in the catalogue. State which icons, variants, sizes, weights and backgrounds were actually reviewed. Automated validation and sampled family review do not establish visual approval for the entire set.
