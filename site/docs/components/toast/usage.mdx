## Using the components

### When to use

- To communicate a nonblocking update from a peripheral application or workflow without interrupting the user's current task.
- To briefly confirm a user action, such as completing an operation, when the result remains visible or available elsewhere.
- To offer an optional action related to an update, provided essential information and recovery actions remain accessible elsewhere.

### When not to use

- As the only indication of an ongoing platform-wide condition. Use [`SystemStatus`](../system-status/usage) for essential maintenance or outage information that must remain available.
- As the only feedback for invalid form fields. Use feedback associated with each field and, where useful, an [error summary](/salt/patterns/forms#error-summary).
- As the only place to explain a failed save or provide essential recovery. Use [`Banner`](../banner) within the affected form or dialog so the message remains with the entered values and recovery actions. See [choosing feedback](/salt/patterns/forms#choosing-feedback).
- When the user must make a decision before continuing. Consider [`Dialog`](../dialog) only when interrupting the workflow is necessary; a routine save failure can be handled in the existing form or dialog.

### Persistence and dismissal

The host application controls when a toast appears and disappears; `Toast` does not provide a dismissal timer. Only dismiss a toast automatically when its message is nonessential or the information remains available elsewhere. Keep toasts containing actions available until the user acts or dismisses them. Dismissing a toast must not remove the only way to recover from a problem.

### Positioning

Position the toast where it won’t interfere with navigation or important content in the user interface, for example, in the lower-right corner of the screen or application viewport.

### Stacking

Stack toasts in chronological order if multiple toasts need to appear on screen at the same time.

When you stack toasts from the top, the newest one should be first. When you stack them from the bottom, the newest toast should be at the bottom.

## Content

A toast notification is typically limited in space, so content should be clear, concise, and short, allowing users to quickly scan the notification and understand the situation and/or next steps.

Configure titles to display the Body Strong typography style and the messaging Body Default typography style across densities.

In addition to text content, toasts can contain any UI elements such as actionable components, like buttons. This allows the user to act on the message without interrupting their current workflow. For example, users can approve or respond to an update without opening a new window. Users should always be able to close or dismiss a toast.

## Import

To import `Toast` and `ToastContent` from the core Salt package, use:

```js
import { Toast, ToastContent } from "@salt-ds/core";
```

To import `ToastGroup` from the lab Salt package, use:

```js
import { ToastGroup } from "@salt-ds/lab";
```
