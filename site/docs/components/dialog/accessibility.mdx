## Best practices

### Accessible name

Provide an accessible name for dialogs by using the visible `DialogHeader` (recommended) or, if design constraints prevent this, apply an `aria-label` attribute directly to the `Dialog` to meet [WCAG 4.1.2](https://www.w3.org/WAI/WCAG21/Understanding/name-role-value.html) requirements.

### Focus

The dialog component will trap focus within the dialog when open. This means that the user will not be able to tab out of the dialog and focus will be set to the first focusable element within the dialog. When the dialog is closed, focus will return to the element that triggered the dialog if it is still available.

### Initial focus

You can control which element receives focus when the dialog is opened by passing an `initialFocus` prop to the dialog component. This prop accepts a number, which indicates the index of the tabbable element within the dialog that should receive focus. If no element is found, focus will be set to the first focusable element within the Dialog. The `initialFocus` can also be a ref to an element within the dialog.

### Focus sequence

- For dialogs that prompt for user confirmation, the call to action button takes focus first.
- For dialogs with destructive interactions, the cancel button takes focus first.

### Returning focus after an action

Choose a return target that lets the user continue their task. When a menu command opens a dialog, the menu item may no longer be mounted when the dialog closes. On Cancel or Escape, return focus to the surviving menu trigger for that record, rather than to the dismissed menu item.

If successful deletion removes the record and its trigger, the application must choose a surviving target. In an ordered worklist, consider the equivalent action on the next record, then the previous record if there is no next record. If the list becomes empty, choose a relevant persistent control or the empty-state heading. These are task-dependent choices, not an automatic selection policy supplied by Dialog. Announce the outcome separately; moving focus is not a success announcement. If the user has already closed the dialog and moved elsewhere, preserve their focus unless the update removes the focused element.

The current Dialog API provides `initialFocus` for opening, but no dedicated return-focus target or after-close callback. Verify these transitions with the current components before adopting a composition that unmounts its trigger. The [WAI-ARIA dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) describes returning focus to a logical workflow target when the invoking element no longer exists.

### Scrollable content

When content in the dialog is scrollable, it will receive keyboard focus (with a visible focus indicator). This allows keyboard and screen reader reliant users to navigate and scroll the content using arrow keys, satisfying [WCAG 2.1.1](https://www.w3.org/TR/WCAG21/#keyboard) and related accessibility requirements.

## Keyboard interactions

<KeyboardControls>
<KeyboardControl keyOrCombos="Tab">

- If focus is in the dialog, Tab sets focus to the next focusable component in the tab order.
- If the last element in the dialog has focus, Tab wraps to the first focusable element in the dialog.

</KeyboardControl>
<KeyboardControl keyOrCombos="Shift + Tab">

- If focus is in the dialog, this action sets focus to the previous focusable component in the tab order.
- If the first element in the dialog has focus, this action wraps to the last focusable element in the dialog.

</KeyboardControl>
<KeyboardControl keyOrCombos="Escape">

- If focus is in the dialog, Escape closes the dialog. Return focus to the triggering element when it remains available; see [Returning focus after an action](#returning-focus-after-an-action) for menu commands and removed triggers.

</KeyboardControl>
<KeyboardControl keyOrCombos="Enter / Space">

- If focus is on a button in the dialog button bar, this action activates the button.
- If focus is on the close button, this action activates the close button, closes the dialog and follows the same return-focus guidance.

</KeyboardControl>
</KeyboardControls>
