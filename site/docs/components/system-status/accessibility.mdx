## Best practices

Check and test any focusable elements included in the system status content.

A system status doesn't have a live region role. A system status that's present when the page loads doesn't need one, because screen readers don't announce live region content that's on the page when it loads. To make it a landmark that screen reader users can find and identify, add `role="region"` and an `aria-label`, as shown in the [placement example](/salt/components/system-status/examples#placement).

If you add a system status after the page loads, or show it again after it's dismissed, render it inside a container with `role="alert"` for an error system status, or `role="status"` for all other statuses. Add the container when the page first loads, then render the system status inside it, because screen readers don't reliably announce a live region that's added at the same time as its content. See the [announced example](/salt/components/system-status/examples#announced).

If one area of the page can show both an error and other statuses, add a container for each role when the page first loads, then render the system status in the container that matches its status.

- **Note:** During your testing, check that the system status is announced using a screen reader.

### Accessible names for actions

Give every action in a system status an accessible name that describes what it does. An icon-only close button needs an `aria-label`, such as "Dismiss system status".

### Focus after dismissal

A system status doesn't manage focus, so focus is lost when a user dismisses it unless you move it. Move focus back to the element that had focus before the user moved into the system status. If there isn't one, move it to a logical place on the page, such as the first interactive element after the system status. See the [announced example](/salt/components/system-status/examples#announced).
